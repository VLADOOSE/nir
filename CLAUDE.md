# CLAUDE.md — АИС «Регион-Мед / West-Med»: тендеры и частные заявки на медоборудование

> **Свежая сессия / после чистки контекста:** сначала прочти `docs/PROGRESS.md` — там «где мы и что дальше» (статус потоков, что сделано в последней сессии, приоритет следующего, как запустить стек). Этот файл (CLAUDE.md) — детальный «мозг» проекта (архитектура/механики/гочи).

## 1. Что это за проект (актуально)

Изначально — дипломная АИС для ООО «Регион-Мед» (РФ). **Диплом защищён; теперь это дорабатывается как реальный продукт** для двух связанных компаний:

- **Регион-Мед (РФ, рубли ₽)** — тендеры на госзакупках (zakupki.gov.ru). По закону в тендерах нельзя называть бренды → заказчик даёт параметры → наш **автоподбор** оборудования из каталога.
- **West-Med (KZ, тенге ₸)** — частные клиники Казахстана. Клиника **прямо называет бренд/модель** (заявка) → проверяем **регистрацию в реестре НЦЭЛС РК** + сорсинг (запрос КП у поставщиков). West-Med закупает у дистрибьюторов; если что-то выгоднее купить в РФ — берётся на Регион-Мед, который продаёт/везёт в Казахстан для West-Med.

Компании **не работают вместе**, у каждой свой рынок. Реализован **глобальный переключатель рынка** (РФ ↔ KZ) — одна БД, колонка `market`, данные одного рынка не видны на другом.

Поток «**Частники**» (West-Med) — главное направление доработок: клиника пишет на **info@westmed.kz** с таблицей оборудования (Excel) → система читает почту, парсит → частная заявка → проверка реестра → подбор поставщиков по брендам → запрос КП дистрибьюторам с **zakup@westmed.kz**.

## 6. Архитектура

Монолит, layered: Controller → Service → Repository → DTO (MapStruct мапперы). REST/JSON. Entity на Lombok, PK BIGSERIAL (IDENTITY). Сервисы — constructor injection без `@Autowired`, `@Transactional` на записи. Контроллеры `@RestController`, «голые» DTO; записи под `@PreAuthorize("hasRole('ADMIN')")` (method security включена в `SecurityConfig`). `@EnableScheduling` на `Nir2Application`. OSIV включён.

### Многорыночность (РФ/KZ) — КРИТИЧНАЯ механика
Изоляция данных по рынку через один `ThreadLocal` **`MarketContext`** + 4 части:
1. **`MarketContext`** (`context/`): `get()` → по умолчанию **`Market.RF`** (НЕ null!), `set(Market)`, `clear()`.
2. **Штамп при вставке:** `MarketStampingListener` (`@PrePersist`) на рыночных сущностях через `@EntityListeners(...)` — ставит `market = MarketContext.get()` при INSERT, если null. Сервисы ещё и пред-штампуют при create (id==null) — defense-in-depth.
3. **Фильтр на чтение:** Hibernate `@FilterDef(name="marketFilter")` объявлен **ОДИН раз на `Tender`** + `@Filter(name="marketFilter", condition="market = :market")` на каждой рыночной сущности. **НЕ переобъявлять `@FilterDef`** на других сущностях. Включает фильтр `MarketFilterAspect` (`@Before` на каждом вызове Spring Data `Repository`): берёт привязанный (tx/OSIV) EntityManager и включает фильтр из `MarketContext`. Без привязанной сессии — НЕ фильтрует.
4. **HTTP:** `MarketInterceptor` (для `/api/**`) ставит `MarketContext` из заголовка `X-Market` в preHandle, чистит в afterCompletion. Фронт: `marketInterceptor` (HttpInterceptorFn) сам вешает `X-Market` на каждый запрос.

**⚠️ Гард `@Scheduled`/фоновых потоков (нет HTTP, нет OSIV):** у фонового потока НЕТ `MarketContext` (дефолт RF) и НЕТ привязанной сессии. Правило: **вызывающий ставит `MarketContext.set(market)` ДО вызова + `clear()` в finally; работа с БД — в `@Transactional`-методе ОТДЕЛЬНОГО бина (не self-invoke)**, чтобы аспект получил привязанную сессию. Пример — приём почты ставит рынок ящика вокруг `@Transactional MailReceiveService.poll()`.

Рыночные сущности: `Tender`, `TenderLot` (через tender), `ActivityApply`, `ApplyItem`, `Facility`, `Distributor`, `MedEquipment`, `PriceRequest`, `InboundEmail`. Общие (без рынка): `MedRegistry`, `EquipmentType`, `HeaderSynonym`, `UserAccount`.

## 7. Модель данных (PostgreSQL, схема — Flyway V1)

- **Справочники:** `facility` (учреждение/клиника; контакты разнесены: last/first/middle_name, phone, email — 1НФ; **+ `region`, `monitor_tenders`** — V13: KZ-больница с `monitor_tenders=true` и БИН в `inn` = источник orgBin-импорта goszakup, см. §5), `distributor` (поставщик: name UK, inn, email; + `@ElementCollection distributor_brand` — какие бренды возит; + `distributor_equipment_type`), `med_equipment` (каталог: name, manufact, equip_type, габариты, weight, spec), `equipment_type`, `user_account`.
- **Реестр:** `med_registry` (≈14072 записи реестра НЦЭЛС РК: reg_number UK, name TEXT, producer, country, reg_date, expiration_date, unlimited). **Наполняется Java-инициализатором из JSON** (`registry/rk-mi-registry-full.json`), не сидом. GIN-trgm индексы `idx_reg_name_trgm`/`idx_reg_producer_trgm`.
- **Слой требований:** `tender` (tender_number, facility_id, status String, deadline nullable, total_cost, description, **`source` PUBLIC_TENDER/PRIVATE_REQUEST**, market), `tender_lot` (tender_id, lot_number, equip_name, equip_type, quantity, max_габариты, **`manufact`** — бренд/модель для частных заявок, required_spec).

    - **Ключ goszakup — СЫРОЙ номер лота площадки** в `source_lot_code` (тот же столбец V12, что у СК-Фармации). Форма номера при этом задокументирована в собственной фикстуре репо (`GoszakupDtoJsonTest`) — тесты промахнулись, потому что кормили синтетическими `lot("1")`. Замер после фикса: **1 → 1305 из 1305**.
    - ⚠️ **Фолбэк по имени — ТОЛЬКО когда имя однозначно** (в очереди ровно одна строка с таким именем). Он нужен, потому что на ПЕРВОМ переимпорте кода нет ни у кого и слияние шло бы на 100 % по имени, а имена внутри тендера НЕ уникальны: 283 из 1305 лотов в 97 группах одинаковых имён (в одном тендере 24 лота «Набор реагентов»). Порядок при этом решает КУЧА — у `Tender.lots` нет `@OrderBy`, у `tender_lot` нет индекса по `tender_id` → Seq Scan, а обновлённая строка уезжает в конец кучи, то есть **строки с работой оператора уезжают вероятнее всех**. Принцип: **потерять лучше, чем молча перепутать** — потерянная спека видна и переразбирается, спека, привязанная к чужому лоту, не видна никак. Замер: 1022 лота сливаются по однозначному имени, 283 честно пересоздаются, 8 из 11 спек остаются НА СВОЁМ лоте.
    - **Два прохода: сперва ВСЕ коды, потом имена по оставшимся.** Жадный проход «код-затем-имя» по каждому входящему лоту мог захватить по имени строку, которую следующий лот сматчил бы по коду.
    - `existing.remove(key)`, а не `get(key)`: при двух лотах с одинаковым ключом `get` отдавал ОДИН И ТОТ ЖЕ управляемый объект → одна строка вместо двух, лот молча исчезал.
    - **Пустой список лотов больше не удаляет строки, а поднимает ошибку** (видна в счётчике прогона). Это достижимо, а не теоретично: `fetchLots` отдаёт `List.of()` при отсутствии items, `parseLots` — пустой список на любой нераспознанной вёрстке ЦЭФ (смена вёрстки, страница троттлинга), а фильтры релевантности падают обратно на ИМЯ объявления → медицински названный тендер проходил и молча обнулял все лоты, засчитываясь как «обновлено».

Простое «непусто» было бы багом: форма лота шлёт модель целиком (`patchValue` + submit), поэтому правка количества тащит с собой неизменённое описание площадки — лот помечался бы разобранным, а очередь (берёт `NULL`/`PENDING`) навсегда теряла бы его из виду. `required_spec` непуст у 1438 из 1490 лотов — там описание с площадки, а не ТЗ.

    - **Двухстадийный запрос (`LotQueryBuilder` — единственное место, где решается, какой текст идёт в подбор):** `identity` (токены ИМЕНИ лота) **отбирают** кандидатов, `qualifier` (токены описания/ТЗ) только **переранжируют** уже отобранное и охват не расширяют. Почему описание не пускать в отбор: названия реестра описывают ТОВАР, а не функцию — замер, пуск описания в отбор раздул «Спектрофотометр» с 3 кандидатов до 278 и утопил верный ответ. Единственное исключение: имя целиком из стоп-слов → пустой identity → токены описания продвигаются в identity (живой случай: 5 лотов с именем ровно «Аппарат», у одного при этом разобранное ТЗ на 5307 симв., начинающееся с «Аппарат ультразвуковой низкочастотный оториноларингологический»). **Попутно починен дефект:** в подбор шёл только `TechSpecExtractor.characteristics(spec)`, а он `null` без якоря разобранного PDF → у 185 лотов `description_ru` (единственное различающее, что у них есть) выбрасывалось целиком, ещё у 39 SK-лотов описания не было вовсе.
    - **Формула — `searchByTokensV2`** (старый `searchByTokens` УДАЛЁН: две живые шкалы скора — источник молчаливых расхождений). `score = F_β(recall_q, precision_d) + BONUS · qualifier_hit_ratio`, где `recall_q` — взвешенное по IDF покрытие запроса названием записи (как было), `precision_d` — **новый член**: доля значимых (≥4 симв.) слов НАЗВАНИЯ ЗАПИСИ, покрытых запросом, со сглаженным знаменателем `nhit/(nden+2)`. Без нормировки по длине записи «Перчатки» давали **147 записей со скором ровно 1.000** — ранжировать было нечем. Сглаживание в одиночку порядок НЕ меняет (монотонно по `nden`), оно убирает взрывной приз односложным названиям; переставляет выдачу только сдвиг баланса к recall (β=1.5).
    - ⚠️ **Знаменатель `precision_d`: слова СВОЕГО скрипта поштучно + вся латиница как ОДНА необъяснённая единица** (`LEAST(count(чужие),1)`). Обе «очевидные» крайности проверены на живом реестре и обе неверны — не упрощать ни в ту, ни в другую сторону. (1) Считать каждое чужое слово: `word_similarity('монитор','monitor') = 0` (разные скрипты не делят ни одной триграммы), то есть латиница — мёртвый груз; у «катетер ASAHI Hyperion Judkins Right…» 60 из 64 слов латинские → скор 0.031, запись недостижима для кириллического лота. По реестру: 75.3 % названий содержат латиницу, 18.6 % массы знаменателя мертво, **1014 записей (7.2 %) выпадали за отсечку ТОЛЬКО из-за латиницы** — а НЦЭЛС это преимущественно импортные бренды, то есть бьёт по самой ценной части. ## 10. Персистентность — Flyway (важно!)

**Данные ЖИВУТ между перезапусками.** Раньше `schema.sql`+`data.sql` с `spring.sql.init.mode=always` дропали все таблицы при каждом старте → рантайм-данные (реальные заявки, письма, клиенты) слетали; и прогон `./gradlew test` тоже затирал базу. Теперь:
- Схема и демо-сид — **миграции Flyway** в `src/main/resources/db/migration/`: `V1__init_schema.sql` (схема **без DROP**), `V2__seed_demo.sql` (демо-данные). Накатываются один раз; дальше «up to date, no migration necessary».
- `application.yaml`: `spring.sql.init.mode: never`, `ddl-auto: none`, `spring.flyway.enabled: true`, `baseline-on-migrate: true`. **`schema.sql`/`data.sql` удалены** — единственный источник схемы это миграции.
- **Менять схему — ТОЛЬКО новыми миграциями V3, V4…** (не править V1/V2).
- Тесты идут на nirdb через Flyway + `@Transactional`-откат (изолированы, базу не затирают).
- **Реестр** (med_registry) Flyway не сеет — наполняет Java-инициализатор из JSON; переживает рестарт (`CREATE TABLE IF NOT EXISTS` + проверка пустоты).
- **Демо-данные пока остаются** (на время разработки). При деплое на сервер: убрать/заменить `V2` на реальные (оставить справочные — реестр, словарь синонимов), применить `ALTER DATABASE <name> SET random_page_cost = 1.1` один раз.
- **Пересоздать БД с нуля:** `dropdb`+`createdb` (UTF-8, см. §5) → старт → Flyway накатит V1+V2, реестр переимпортируется. Иначе Flyway упрётся в существующие таблицы.

## 11. Реестр-матчинг и производительность

- Примитив `MedRegistryRepository.findCandidates(name, manufact, limit)` (нативный, `word_similarity` `<%` — индексо-дружелюбный; раньше был оператор `%` similarity → seq scan по 14k на длинных названиях смет ~600мс). Скоринг 0.6·производитель + 0.4·название. `RegistryMatchService.findCandidates` обрезает названия до 80 символов.
- **`ALTER DATABASE nirdb SET random_page_cost = 1.1`** — обязательно, иначе планировщик на маленькой таблице (14k) игнорирует GIN-индекс и уходит в seq scan. Применено к nirdb; в V1 закомментировано (ALTER DATABASE нельзя в транзакции инициализации); на новой БД применить вручную.
- **Список частных заявок НЕ считает реестр** (было 10.6с → 6мс): показывает только число позиций; полный реестр-статус строк — только в карточке (`findById`). Карточка сметы (16 строк): ~9с → ~0.2с.

### UI-kit — глобальный слой примитивов (`src/styles.scss`)

Те же правила были скопированы по компонентам (`.empty` в 14 файлах, `.subtitle` в 13, `.btn-cancel` в 12, база `th, td` в 11, `.badge*` в 11), поэтому вместо ~845 точечных замен построен один слой, а компоненты зачищены от дублей.

**Почему это безопасно:** Angular-scoped правило компилируется в `.btn[_ngcontent-x]` (специфичность 0,2,0) и всегда перебивает глобальный `.btn` (0,1,0). Слой «спит» под каждым компонентом и просыпается ровно тогда, когда локальный дубль удалили. Фундамент схемы: в приложении **нет ни одного `ViewEncapsulation.None` и `::ng-deep`** (проверено финальным ревью) — если появится, допущение подмоется.

**Что в слое:** `.btn` + роли (accent / нейтраль / danger / warn / outline), `.badge` + статусы (`badge-<СТАТУС>`, `badge-pr-*`, `badge-d-*`), `.subtitle`, `.counter`, `.empty`, `.field-error`, `.error-banner`, `.form-actions`; цветовые дефолты `h2/h3`, `th/td`, `input/select/textarea`; `color-scheme` + `accent-color` для нативных контролов.

**Правило дополнения:** цвет и общая геометрия примитива — в kit, раскладка (`margin`/`flex`/`width`/`position`) — в компоненте.

**Токены (20, объявлены в обеих темах):** `--app-bg/--surface/--surface-2/--border/--text/--text-muted/--accent/--accent-hover/--accent-contrast/--danger/--warn/--success/--header-bg/--header-text/--shadow` плюс введённые этой работой `--danger-text/--warn-text/--success-text` (см. ниже), `--shadow-lg` (крупные тени модалок), `--shadow-color` (сила тени боковых дроверов — направленность остаётся на месте использования, потому что дроверы зеркальные).

### Главное правило выбора токена: смотри на СЛОТ CSS, а не на исходный хекс

- `color:` → **текстовый** токен (`--danger-text`/`--warn-text`/`--success-text`/`--text`/`--text-muted`)
- `background`, `border-*`, `box-shadow`, подложка в `color-mix(...)`, заливка шкалы → **заливочный** (`--danger`/`--warn`/`--success`/`--surface`/`--surface-2`/`--border`)

⚠️ **Зачем разделены.** Изначальная таблица слала в один токен и заливки (`#10b981`, `#ef4444`), и тёмные цвета текста (`#065f46`, `#991b1b`, `#92400e`). Для заливки верно, а как цвет текста на светлом тинте давало **2,1–3,4:1 в светлой теме** («★ победитель» 2,13:1, чипы стадий 1,91:1). Дефект уехал в прод ещё с тёмной темой 2026-07-19 и жил в 37 местах. Текстовые токены в светлой теме равны исходным тёмным значениям (то есть это ВОЗВРАТ точности), в тёмной — заливочным. У `--accent` текстового близнеца нет намеренно: 6,18:1 на белом, но ровно 4,50:1 на `--surface-2` — глубже не сажать.

**Две формулы тинта, не перепутать:** чип/бейдж — `color-mix(… 15%, transparent)` + текстовый токен; подсветка ОБЛАСТИ (строка, ячейка, карточка, панель) — `color-mix(… 8%, var(--surface))` + `border-color`. Область **никогда** не `--surface-2`: подсветка совпадёт с фоном панели и смысл инвертируется (баг `6b8dc3f`). Токен берётся ОТ ИСХОДНОГО ЦВЕТА, а не от «смысла вообще».

**Санкционированные исключения — цвета, которые остаются хексами** (все с комментарием на месте): фикс-цветные кнопки `#0e9f6e` («КП»), `#6366f1` («ТЗ»), `#8b5cf6` (bulk); заливки тостов `#059669`/`#dc2626`/`#1a56db`; `.role-badge.role-admin` в шапке; палитра серий графиков (канвас не понимает `var(--…)`). Общее у них одно: белый текст на насыщенной заливке поверх произвольного фона — токенизация ломает контраст, потому что в тёмной теме `--success`/`--danger` осветлены.

**Графики** (`chart.component.ts`): оси/сетка/подписи на токенах, серии — палитра хексами, `colors[0]` осветлён `#1a56db → #3b82f6` (брендовый синий на тёмной подложке давал 2,0:1). Перекраска при смене темы — `MutationObserver` на `data-theme`, иначе chart.js держал бы цвета прошлой темы до навигации.

⚠️ **Ловушка, стоившая двух фикс-раундов и одной регрессии:** `.btn-<роль>` из kit даёт **только цвет**; геометрию и `:disabled` даёт базовый `.btn`. В приложении четыре исторические кнопки со `class="btn-primary"` без `btn` — у них `:disabled` из kit не достаёт, а `:hover` достаёт, и Chrome применяет ховер к заблокированной кнопке. Либо дописать `btn` в разметку, либо повторить геометрию локально теми же значениями плюс `:disabled`/`:disabled:hover`.

⚠️ **Инлайн-цвет в разметке или в TypeScript перебивает любой лист** и из `styles` не чинится. Такие места вычищены (колонка «Реестр» в `private-requests` давала 2,1:1; чип стадии собирался в методе `stageChipStyle`), но при добавлении нового кода — не заводить заново.

**Фильтры тендеров — отдельный компонент `app-tenders-filters` (2026-07-19, `tenders-filters.component.ts`):** презентационный, свой style-бюджет (разгружает большой `tenders.component`). ### Мобильные карточки: два режима (доведено 2026-07-29)

Прежний паттерн был один и **механический**: `<table class="responsive-cards">` + `data-label` на каждой `<td>`, и ≤900px каждая колонка становилась строкой «подпись: значение». Горизонтального скролла он убирал, но на широкой таблице давал простыню: `/applies` — 9 колонок, карточка **307px**, 2,7 на экран, **51 экран прокрутки** на 141 заявку. Экран как бы адаптирован, а пользоваться нельзя.

Теперь режимов два, второй включается **opt-in классом** `card-grid` на той же таблице:

| Режим | Класс | Когда брать |
|---|---|---|
| **Механический** — ячейка = строка «подпись: значение» | `responsive-cards` | карточка ЗАПИСИ: характеристики читают подряд, записей мало |
| **Спроектированный** — строка = CSS-грид с областями | `responsive-cards card-grid` | СПИСОК: много однотипных записей, которые сканируют глазами |

**Механизм спроектированного режима** — строка становится гридом, а ячейки раскладываются по именованным областям через **адресацию по `data-label`**:

```scss
@media (max-width: 900px) {
  .applies-list tr {
    grid-template-columns: 1fr auto;
    grid-template-areas: "num status" "cust cust" "sum cnt" "act act";
  }
  td[data-label="Номер тендера"] { grid-area: num; font-weight: 600; }
  td[data-label="Статус"]        { grid-area: status; justify-content: flex-end; }
  td[data-label="ID"]            { display: none; }
  td:not([data-label])           { grid-area: act; }   /* колонка действий */
}
```

Почему так, а не иначе:

- **Адресация по `data-label`, а не по `nth-child`** — порядок колонок меняется, раскладка не ломается; и правило читается как документация.
- **Разметка НЕ дублируется.** Отдельный блок карточек для мобилки + таблица для десктопа удваивают шаблон и разъезжаются при первой правке.
- **Десктоп не трогается** — всё внутри `@media (max-width: 900px)`. Это проверялось замером `getComputedStyle` до/после на каждом экране; расхождения ловились вплоть до 0,1px (обёртка значения в `<span>` срезала пробел — лечится `&ngsp;`).
- **Скрывать (`display: none`)** то, что не участвует в просмотре списка: технические id, даты создания, служебные счётчики. Данные не теряются — всё видно в карточке записи.
- **`::before` с подписью выключается** (смысл несёт позиция), но включается точечно там, где значение без подписи нечитаемо — например голая `1` у количества или длинный номер тендера.

**Порог: запись выше ~140px считается простынёй** и переводится на `card-grid`. Он не произвольный — по нему специально переводили `users` (156→85px) и `registry-reconciliation` (200–259→106px), которые по числу колонок казались приемлемыми, и им же ужимали историю запросов в карточке оборудования (186→84px).

**Если таблица одна на несколько экранов — раскладка должна быть одна.** Грид импорта D1 живёт и в `private-requests`, и в `inbound`; когда шапки разъехались по цвету, это чинили как дефект.

**Меню «⋯»** для действий строки — в глобальном слое рядом с `card-grid` (разметка и стили; логика открытия/закрытия остаётся в компоненте, там `@HostListener('document:click')`). Брать, когда действий больше двух.

**Приём «N видимых чипов + счётчик» чистым CSS**, без правки TypeScript: лишние чипы уходят через `position: absolute; visibility: hidden; counter-increment`, число печатает `::after` через `:has()`. ⚠️ Именно `visibility: hidden`, а не `display: none` — на последнем счётчик не работает, элемент не создаёт бокс. Эталон — чипы брендов в `distributors`.

**Матрица на телефоне не работает в принципе** — если и строк, и колонок произвольное количество, её надо переворачивать. Сравнение предложений (лоты × поставщики) на ≤900px стало карточкой-на-лот со списком предложений; сделано переиспользованием механического режима с **динамической** подписью ячейки (`[attr.data-label]="s.distributorName"`), TypeScript не тронут.

⚠️ **Тач-таргеты:** глобальное `button, .btn, a.btn { min-height: 40px }` покрывало только кнопки, из-за чего поля и селекты оставались 26–34px (хуже всех — селектор рынка в шапке, он на каждом экране). Теперь правило расширено на `select` и `input`, кроме чекбоксов и радио.

⚠️ **Как мерить, чтобы не обмануться** (на всём этом наступали): `browser_navigate` в Playwright **сбрасывает вьюпорт на 1280** — перед мобильным замером проверять `window.innerWidth`, иначе намеришь десктоп и решишь, что правила не сработали. И `scrollWidth > clientWidth` **не означает прокрутку**: при `overflow: hidden` + `text-overflow: ellipsis` это работающее многоточие, пользователь такой элемент промотать не может — в зонде отсекать по `overflow-x`.

Спека/план — `docs/superpowers/{specs,plans}/2026-07-25-tender-card-lots-rework*`.

## 14. Ключевые gotchas / уроки

- **`./gradlew test` раньше затирал nirdb** (schema.sql DROP) — теперь нет (Flyway). Если данные «пропали» — проверь, что используется Flyway-путь.
- **`@FilterDef` — только на `Tender`**; дубль на новой сущности = коллизия при старте.
- **`@Scheduled` без `MarketContext`** → дефолт RF + нет фильтра (см. §6).
- **JPA orphanRemoval**: лотами управлять через коллекцию, не `repository.delete`.
- **Mail.ru**: только пароль приложения; реальные письма — вложенный multipart + MIME-имена; обязательны рекурсивный обход + декод.
- **pg_trgm + кириллица**: nirdb обязан быть UTF-8 локалью; `random_page_cost=1.1` чтобы юзался индекс.
- Ручной клик-тест ловит то, что юнит-тесты (минуя `@Valid`) пропускают — проверять фичи в браузере.
- **Bash cwd персистит между вызовами**: `cd frontend && npm run build` оставляет cwd во `frontend` → следующий `./gradlew`/`git` падает («No such file»). git/gradlew — из корня (компаунд `cd /Users/vlad/IdeaProjects/AIS && …`).
- **Edit больших файлов** (`RegistryMatchService`, `tenders.component.ts`): фоновый автоформат иногда дублирует вставленный метод или съедает соседнюю сигнатуру (ловили дубль `adoptForLot` + съеденный `applyAction`). После крупной правки — `grep -c "имяМетода"` на дубли + `./gradlew compileJava`; Edit может упасть «File has not been read yet» после фоновой модификации — перечитать и повторить.
- **pg_trgm `word_similarity` / `<%`**: чувствителен к длине запроса (порог 0.6 отсекает длинные фразы целиком) → лот-матч по значимым токенам, не по всей строке (§8 `LotQueryTokenizer`). Индекс живёт только если фильтр `EXISTS(IN(join tok <% name)) OFFSET 0`, а не голый `EXISTS` (иначе seq scan 650мс, см. §8 `searchByTokensV2` — старый `searchByTokens` удалён, приём с `OFFSET 0` перенесён в него).
- **`@media` в inline-стилях компонента — ТОЛЬКО В КОНЦЕ блока styles**: при равной специфичности позднее базовое правило перебивает более раннюю @media-переопределялку (ловили на `.stat-cards` дашборда — мобильный 2×2 молча не применялся). Плюс grid-гоча: `repeat(N, 1fr)` НЕ сжимается ниже min-content → на узком экране переполнение, а не ужатие.
- **Динамические lucide-иконки могут прийти ПУСТЫМ `<svg>`** (без path — ловили на `lucideIcon="menu"`: кнопка-гамбургер была в DOM, но невидима). Для критичных иконок шапки/логина — инлайн-SVG с захардкоженными path, не lucide. Проверка: `svg.children.length > 0`, а не «svg есть».
- **Оверлей ошибок `ng serve` ЗАЛИПАЕТ и врёт** (ловили дважды за сессию 2026-07-27: `TS2531` и `NG1010 'imports' must be an array`). Дев-сервер показывает ошибку от ПРОМЕЖУТОЧНОГО сохранения файла и держит её в открытой странице уже после того, как код починен — особенно заметно, когда файл правит субагент. **Не верить оверлею: проверять `git status` + `npm run build` + перезагрузку страницы.** Оба раза дерево было чистым, сборка зелёной, а после reload оверлей исчезал.
- **Живая проверка на работающем сервере ловит то, что не видит ни код-ревью, ни сборка** (сессия 2026-07-27): `PUT /api/lots/{id}` с `equipTypeId: null` отдавал **200** и молча не снимал тип; панель КП после adopt брала дореестровый объект лота и в письмо поставщику уходил голый лот вместо модели с РУ. Оба дефекта выглядели корректно в коде. Правило §2 «проверять вживую перед словом "готово"» — не формальность.
- **Замер производительности проверять на подходящих данных.** Замерял стоимость change detection на тендере с 50 лотами и получил «3 мс» — а у того тендера **ноль запросов КП**, то есть тяжёлая часть (обход `priceRequests × items`) в замер не попала вовсе. Для лотовых экранов брать тендер и с лотами, и с КП, и с введёнными ценами.
- **Метрика с ПОЛОМ поощряет ровно то поведение, от которого уходишь** (заход 2026-08-01, реестр-подбор). «Корректность зоны» выглядела как мера качества, но политика «всегда отвечать *не могу*» брала на ней 52/71 = 73 %. Первая редакция калибровки показала 58/71 — и покупала эти шесть кейсов СОКРЫТИЕМ трёх верных ответов, которые лежали на первом месте выдачи. Правило: прежде чем ставить гейт на агрегат, посчитать, сколько на нём берёт вырожденная политика; если много — гейт разбирать на компоненты, которые молчание не может улучшить.
- **Зелёный тест, который НЕ МОЖЕТ упасть, — это отсутствие покрытия, замаскированное под покрытие.** За заход поймано пять раз, из них показательные три: assert, стоявший в 0.037 от вакуумности (двинули бы порог на 0.05 — молча прошёл бы, унеся последнее покрытие своей ветки); тест «слабый матч после неудачного ТЗ» на лоте с НУЛЁМ кандидатов (код возвращался на ветке `isEmpty` и до чтения `techSpecStatus` не доходил вообще — javadoc утверждал обратное); гард `rivals` с фикстурой, у которой `rivals=0` (`0 <= 0` проходит при ЛЮБОМ пороге, в том числе при снятом гарде). **Лечение — прогон МУТАЦИЕЙ:** ломаешь фикс/константу и убеждаешься, что падает ровно нужный тест. ⚠️ Мутации, затрагивающие ОДИН И ТОТ ЖЕ вызов, гонять по одной: две сразу дали «похожий на успех» результат, потому что первая обесточила вторую.
- **`LIMIT` без `ORDER BY random()` — это не выборка, а сплошной блок соседних id.** Замер распределения зон «2 из 70 CONFIDENT» занижал реальную долю в 2.5 раза, а долю `NEED_TECH_SPEC` завышал втрое. Пересчёт на полной популяции (1344 лота) дал другую картину.
- **Узкий `LIMIT` в дизъюнкции даёт результат, НЕОТЛИЧИМЫЙ от честного «не найдено».** Дважды за заход «в реестре такого нет» оказывалось ложью: первые 8 совпадений OR-запроса пришлись на другую ветку, и запрос «успешно» вернул пусто. Плюс к этому: проверять отсутствие надо ПО ФУНКЦИИ изделия, а не по существительному из названия лота (искомое бывает зарегистрировано внутри набора, в имени которого этого слова нет вообще).
- **Настоящий `OutOfMemoryError` НЕ проявляется как падение теста** — JUnit считает его невосстановимым и убивает gradle-воркера («Could not complete execution for Test Executor»). То есть регрессия выглядит как инфраструктурный сбой. Для проверки веток `catch (Error)` брать локальный подкласс `Error` (ветка кода та же), а настоящий OOM оставлять там, где его доказуемо ловит `assertThatThrownBy`.
- **`exit 137` (SIGKILL от OOM-киллера контейнера) не закрывается никаким `catch`** — java-код при нём не выполняется вовсе. Всё, что должно пережить убийство процесса, пишется в БД ДО опасной операции, а не в обработчике ошибки.
- **Проба сохранности обязана проверять ПРИВЯЗКУ артефакта к сущности, а не факт его выживания.** Проба «11 из 11 спек сохранены» считала выжившие ТЕКСТЫ и была слепа к тому, что спека уехала на чужой лот вместе с чужими количеством и ценой. Ошибка привязки не краснеет нигде и заметна только при чтении данных руками.
- **Проверять данные надо ТЕМ ЖЕ кодом, который работает в проде, а не переписанным «на скорую руку» правилом.** Перепроверка списка тендеров на удаление шла через regex-разбор HTML и объявила 11 страниц «неизвестной вёрсткой», хотя вручную в них видны нужные заголовки: шапка свёрстана так, что `<tr>…</tr>` регуляркой не ловится, а Jsoup битую разметку нормализует и разбирает верно. Реимплементация расходится с оригиналом ровно на кривых входах — то есть там, где проверка и нужна. Настоящий код дёшево дёргается из `jshell --class-path build/classes/java/main:<jsoup.jar>`.
- **Исчезновение теста не краснеет ни на одном прогоне.** Блочная замена в тестовом файле проглотила три теста, включая единственное покрытие только что добавленной ветки; поймано сверкой диффа с деревом, а не прогоном. После крупных правок тестов сверять список тестов, а не только «зелёно».
