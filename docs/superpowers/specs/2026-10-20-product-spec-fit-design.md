# Сверка ТЗ с нашими товарами — дизайн

**Дата:** 2026-10-20. **Статус:** дизайн согласован с оператором по частям (1–6) в чате 2026-10-20, спека — на просмотре.
**Связь:** переделка сверки блока «Наша продукция в тендерах» (спека `2026-10-19-product-watch-design.md`, CLAUDE.md §8);
поиск по стране, группы, планы закупок и «Найти тендеры» остаются как есть. Отзыв оператора — CLAUDE.md §16
«Наша продукция в тендерах» → «Отзыв оператора 2026-10-20».

## 1. Зачем

Первый день поиска по стране на проде (2026-10-20): найдено 29 тендеров «с нашим товаром», оператор — «сыпет всё подряд».
Отметка «🏷 наш вид» ставится по слову вида изделия, а ТЗ бывает написано под чужой бренд: 17828560-1 «Электрокоагулятор»
(Кызылорда, 15,7 млн ₸) — ТЗ на BOWA ARC 303 (Германия, «Өндіруші: BOWA немесе … баламасы»). «★ точно наше» пусто:
бренд в тендерах почти не пишут (закон), а «ТЗ списано» срабатывает, только если ТЗ взято из описания нашего товара.

Оператор (дословно): «возьмёшь каждый товар с сайта, проверишь регистрацию и с ndda.kz возьмёшь описание каждого товара
по спецификации и потом … когда тендер новый выходит сравниваться ТЗ с ТЗ нашими товарами»; «неужели без LLM и денег
нельзя сделать точечней распознавание»; «переработать и UI разбора ТЗ, неудобно читать сравнивать особенно с телефона».

Цель: по каждому новому тендеру понимать, **можно ли подать наш товар** (не «тот же вид», а «наш проходит по ТЗ»),
с причинами; в Telegram — только такие.

## 2. Решения разговора (2026-10-20)

1. Сообщения — в свою тему «Тендеры (наши товары)» (тема 95), только «★», только если наши лоты тендера от 1 млн ₸ —
   **сделано и в проде с 07:52 UTC** (`ProductNotifyPolicy`, `TELEGRAM_PRODUCTS_THREAD_ID`, ветка `fix/product-watch-topic`).
2. Сверка — **подход A**: требования ТЗ поштучно против характеристик нашего товара, с ✓ / ✗ / ≈ / «нет данных» и
   причинами; без LLM. Полный объём (≈ 2,5–3,5 дня).
3. Характеристики основных аппаратов Фотек и Ориона — **собрать с официальных сайтов производителей, показать оператору,
   после его «да» внести на westmed.kz** (АИС берёт их с сайта — один источник).
4. «Подходит» — **без провалов и большинство ✓**: ни одного ✗, подтверждено не меньше половины требований (и не меньше
   трёх), у товара **действует РУ**; иначе «похоже — проверьте» / «не подходит: причина» — только в АИС.
5. «ТЗ под чужой бренд» — пометка; наш аналог всё равно сверяется (в ТЗ обычно «или эквивалент»).
6. Экран: вердикт у лота, блок «Сверка с нашим товаром» (на телефоне — одна колонка), «Требования ТЗ» списком у любого
   разобранного ТЗ, вкладка «Наша продукция → Товары».
7. «📋 Для ИИ» — готовый текст по тендерам с нашими лотами для вставки в Claude (веб / терминал) или Gemini: запрос,
   ТЗ, наша сверка, наши товары с РУ и характеристиками, похожие записи реестра НЦЭЛС. ИИ внутри АИС нет.

## 4. Карточки наших товаров

### 4.1 Источники
Товар сайта (`site_product`, загрузка каталога — как сейчас, админ-API учёткой ais@): название, описание, характеристики
списком, № РУ. По № РУ — запись `product_registration` (§4.2). Пересчёт сверки открытых тендеров — после загрузки
каталога и после проверки РУ (§6.5).

### 4.2 Проверка РУ (`product_registration`)
Раз в сутки после загрузки каталога (и по «Обновить» на «Наша продукция») — по каждому разному № РУ товаров сайта
(сейчас 37), пауза 300 мс, свой поток каталога:
1. `list` с `regPeriod=1` и точным номером → **действует** (дата, «бессрочно» / «до …»);
2. нет — `list` с `regPeriod=2` → **истекло** (дата окончания);
3. нет и там — **не найдено**;
4. для найденных — карточка (`MtMainGetById`: назначение, область применения, краткие характеристики, класс риска)
   и комплектность (`MtComplectList`).

Сеть — вне транзакции, запись — своим бином (как `RegistryDetailWriter`). Сбой номера — прежние данные остаются,
в итоге проверки «ошибок N». Номер РУ на сайте с лишними пробелами / другим «№» — нормализуется перед запросом.
Сайт без № РУ — «РУ не указано» (тоже «не продать»).

### 4.3 Характеристики для сверки
Из товара собирается список фактов «параметр — значение(я) — единица — откуда»:
- **сайт, характеристики списком** — основной источник (каждая строка `attributes` — факт; числа и диапазоны — по
  правилам §5.2, «да» / «есть» — признак);
- **карточка РУ** — числа с единицами из кратких характеристик («Масса блока 4,5 кг», «Потребляемая мощность 210 ВА»);
- **описание сайта и назначение РУ** — только как текст для признаков (§5.3) и числа с единицами из него.

Факты считаются при сборке снимка каталога (`CatalogSnapshot`), не хранятся.

### 4.4 Пробелы Фотек и Ориона
Разовая работа данных (не код АИС): основные аппараты Фотек (ЭХВЧ-80-03, ЭХВЧ-350-01 / 02 / 03, ЭХВЧа-140-02, ONYX /
ONYX-A, АСД и др.) и 14 товаров Ориона без характеристик — характеристики **только с официальных сайтов производителей**
(как в V9: per-claim источник). Таблица «товар — характеристика — значение — ссылка» — оператору; после «да» — внесение
через админ-API сайта (`PATCH /api/admin/products/{id}`, поле `attributes` заменяет список целиком → отправляется
прежний список + новые строки; уже заполненное не трогается); после — «Обновить» каталог в АИС. Скрипт разовый,
в репозиторий — только таблица данных (`docs/research/2026-10-20-fotek-orion-attributes.md`).

## 5. Требования ТЗ

### 5.1 Откуда текст
Разобранное ТЗ лота (`required_spec` при `tech_spec_status = OK`): русская часть (`TechSpecExtractor.russianSection`),
раздел характеристик (после «характеристики закупаемых товаров» / `characteristics`); нет ТЗ — описание лота площадки.
Строки, разорванные PDF, склеиваются: строка без «;» / «:» / «.» в конце, а следующая — со строчной буквы, цифры или
единицы, — продолжение. Требование — пункт: через «;», с новой строки, после «-» / «•» / «–».

### 5.2 Требование с числом
Параметр (текст до числа) + условие + число(а) + единица:
- условие: «не менее / не ниже / не меньше / ≥» → нижняя граница; «не более / не выше / не больше / ≤» → верхняя;
  «от X до Y», «X–Y» → диапазон; «до X» — по смыслу параметра: у массы, габаритов, шума, потребляемой мощности и времени
  выхода на режим — «не более X» («вес до 10 кг»), у остального — «наш должен дотянуться до X» (верх нашего диапазона ≥ X:
  «вакуум до 75 кПа», «мощность до 300 Вт»);
  «примерно / около / просто число» → точное значение с допуском;
- единицы и семейства (перевод внутри семейства): мощность Вт / кВт (ВА — отдельно, не путать с Вт); частота
  Гц / кГц / МГц; длина мм / см / м; масса г / кг; объём мл / л; поток л/мин; давление кПа / мм рт. ст. (перевод
  1 кПа = 7,5 мм рт. ст.); напряжение В; ток мА / А; время с / мин / ч; %, дБ; каналы; шт;
- **число без единицы** — счётное требование («Количество ламп — 1», «каналов — 12»);
- **разрежение и вакуум** — по модулю («−80 кПа» = 80);
- «X × Y × Z мм» (габариты) — три числа, сравниваются поосевые (как `SpecConstraintExtractor`).

### 5.3 Признак
Пункт без числа, с «наличие / возможность / режим / функция / тип / система / защита / индикация / регулировка» или
короткий «параметр — значение» без числа («Тип крепления — настенно-потолочный», «Лампа в комплекте — да»): значимые
начала слов (≥ 3 букв, без служебных) сверяются с текстом нашего товара (название, описание, характеристики, назначение и
характеристики РУ, комплектность). Небольшой словарь синонимов параметров (разрежение ~ вакуум, производительность ~ поток,
способ размещения ~ тип крепления, ёмкость ~ объём …) — для имён фактов и признаков.

### 5.4 Что не требование
Назначение, область применения, «предназначен для», «позволяет», «может применяться», номер закупки и лота, место и срок
поставки, количество и единица лота, гарантия, документы (РУ, сертификаты, паспорт), обучение, монтаж — в сверку не идут.
Пунктов меньше двух — «требований нет» (§6.3).

### 5.5 Чужой бренд
Признаки (калибровка на наборе, §13):
- поля «Производитель: X», «Өндіруші: X», «Модель: X», «Страна производитель: X» (страна не РФ / РК — «под …, Германия»);
- слово латиницей рядом с кодом модели, повторённое в ТЗ («BOWA ARC 303», «ZOLL AED»), кроме стоп-списка
  технических сокращений (SpO2, TFT, USB, DDP, ISO, IP …);
- бренды из производителей реестра НЦЭЛС (первые значимые слова латиницей; без Medical / Systems / GmbH …).

Не чужой бренд: наши бренды и модели (Фотек / FOTEK, Аксион / Axion, ЭМА, Орион, Монитор, ONYX, ACTITON, ТЕРМОШОВ …),
совместимость — «типа X», «разъём X», «датчик типа X», «совместим с X». Результат — `foreign_brand` («BOWA», страна —
если указана).

## 6. Сверка и вердикт

### 6.1 Кандидаты
Сверка — у отметок групп вида (не «Наши бренды и модели»: там назван наш товар). Кандидаты — товары группы, сначала
самые похожие по тексту (`SimilarProducts`), до 3. Лучший — без ✗ и с наибольшей долей ✓, при равенстве — больше ✓,
затем действующее РУ. Варианты одной модели («со стойкой / без стойки») — одной строкой «ещё: …».

### 6.2 Отметка по требованию
Факт нашего товара для требования: та же единица (семейство) и наибольшее совпадение имени (синонимы §5.3); единственный
факт этого семейства у товара — берётся и без совпадения имени.
- ✓ — проходит (граница соблюдена, диапазоны пересекаются, точное — в допуске ±15 %, признак — ≥ 60 % слов найдено);
- ✗ — не проходит: **только по числам**, когда у нас есть значение и оно нарушает условие («в ТЗ не менее 300 Вт —
  у нас 80 Вт»); счётное без условия — тоже ✗ при несовпадении («ламп: в ТЗ 1 — у нас 6»);
- ≈ — отличается: точное значение без условия, у нас другое больше чем на 15 %; не провал и не подтверждение;
- ? — нет данных.

### 6.3 Вердикт лота × товара
Доли — от всех требований лота (§5.2 и §5.3, без «не требований» §5.4).
- **FITS «✓ подходит наш X»** — ни одного ✗, ✓ ≥ 50 % требований и ✓ ≥ 3, РУ товара **действует**;
- **FITS_NO_RU «подходит по ТЗ, но РУ истекло / не найдено / не указано»** — то же, РУ не действует (не шлём);
- **PARTIAL «◐ похоже — проверьте»** — ✗ нет, но ✓ < 50 % или < 3;
- **NOT_FIT «✗ не подходит: <первое ✗>»**;
- **NO_REQUIREMENTS** — требований < 2 (ТЗ нет или одно название): сверки нет, отметка — «🏷 наш вид».

Пороги (50 %, 3, ±15 %, 60 %) — константы рядом с замерами, калибровка на наборе (§13).

### 6.4 Уровни
`ProductMatchLevel`: TYPE < **FITS** < NAMED < COPIED. Вердикт FITS поднимает отметку TYPE до FITS (NAMED / COPIED
остаются). «★»-уровни для Telegram (`ProductNotifyPolicy` STAR) — FITS, NAMED, COPIED; в карточке и в сумме порога — только
их лоты. «ТЗ под X» — свойство отметки, уровень не меняет. Сообщённый FITS, ставший COPIED, — «★ Уточнение» (как сейчас).

### 6.5 Когда считается
В `ProductMatchService.evaluate` (поиск, импорт, разбор ТЗ, пересчёт), чистой функцией над снимком каталога (с фактами и
РУ, §4) и ТЗ лота; результат — в отметке (§10). Пересчёт открытых тендеров — после загрузки каталога и после проверки РУ
(существующий молчаливый пересчёт, `ProductRematchService`): тендер, ставший FITS, уходит в Telegram обычным порядком.

## 7. Telegram (тема 95)
Сообщение «🏷 Наш товар в тендерах: N» — разделы «✅ Подходит наш товар» (FITS), «★ Точно наше» (NAMED / COPIED),
«★ Уточнение»; по тендеру: предмет, заказчик · регион, по нашему лоту — «<лот> — N шт.: <наш товар> — 5 из 8 требований
(нет данных: 3)», для ТЗ под чужой бренд — «ТЗ под BOWA — наш аналог по ТЗ проходит»; сумма, приём до, площадка и №,
«Открыть в АИС». Со звуком — все «★» и FITS. Порог 1 млн ₸ и режим — `ProductNotifyPolicy` (без изменений).
PARTIAL / NOT_FIT / FITS_NO_RU / TYPE — только в АИС.

## 8. Экраны

### 8.1 Лот в карточке тендера (`tender-lots`)
- **Свёрнутый:** вместо «🏷 <группа>» — вердикт: «✓ подходит: ОМХ-5/80 «Аксион» · 5 из 8» (success), «◐ похоже —
  проверьте» (warn), «✗ не подходит: мощность» (muted), «подходит по ТЗ, РУ истекло» (warn); рядом серым «ТЗ под BOWA»;
  ★-отметки — как сейчас. Нет сверки — «🏷 наш вид» как сейчас.
- **Развёрнутый — «Сверка с нашим товаром»** (вместо сплошного текста ТЗ, над ним): наш товар (ссылка на сайт ↗),
  статус РУ, счёт «✓ 5 · ✗ 0 · ≈ 0 · нет данных 3», «ещё: …» (переключает сравнение); строки требований — сначала ✗,
  потом ≈, ✓, «нет данных»: отметка, текст пункта ТЗ (кратко), под ним «у нас: <значение> (сайт / РУ / описание)» или
  «нет данных». На телефоне — одна колонка, без таблиц, цели 40 px. Ниже — «▾ Полный текст ТЗ» (как сейчас).
- **Лот без нашей отметки, с разобранным ТЗ** — тот же список «Требования ТЗ: N» без отметок (переделка чтения ТЗ).

### 8.2 «Наша продукция → Товары» (вкладка страницы `/product-groups`)
Все товары каталога рынка KZ: название (ссылка на сайт), бренд, РУ (№, «действует до … / бессрочно», «истекло …»,
«не найдено», «не указано»), характеристик N или «нет характеристик». Фильтры: «Все / Без характеристик / РУ истекло
или не найдено». Сверху — «Проверено РУ: ЧЧ:ММ», у админа — «Обновить» (каталог + РУ).

### 8.3 «Тендеры»
Фильтр «Наш товар»: «★ подходит или точно наше» (FITS / NAMED / COPIED), «любой», группа — как сейчас. Чип в списке —
вердикт лучшего лота (как в §8.1, коротко).

## 9. «📋 Для ИИ»

### 9.1 Где
- карточка тендера — «📋 Для ИИ»: этот тендер, все его наши лоты, текст ТЗ целиком (раздел характеристик);
- «Тендеры» при фильтре «Наш товар» — «📋 Для ИИ: N тендеров»: до 15 с ближайшим сроком приёма (открытые), ТЗ — до
  4000 знаков на лот; больше 15 — тост «скопировано 15 из N».
Текст собирает сервер; фронт копирует в буфер (`navigator.clipboard.writeText` из нажатия; на iPhone тоже), тост
«Скопировано: 3 тендера, 18 тыс. знаков — вставьте в Claude или Gemini». Весь текст — не длиннее 120 000 знаков
(дальше — «…обрезано»).

### 9.2 Текст
Запрос (в начале, дословно):

```
Ты помогаешь компании West-Med (Казахстан, поставка медицинского оборудования) разобрать государственные тендеры.
Ниже — тендеры, в которых, возможно, есть наше оборудование: по каждому лоту — требования технической спецификации (ТЗ),
наша автоматическая сверка, наши товары-кандидаты с характеристиками и регистрацией в РК и похожие изделия из реестра
НЦЭЛС РК.

Для каждого лота:
1. Коротко — какое оборудование требуется и его ключевые параметры.
2. Под какую модель и производителя похоже написано ТЗ; не уверен — «не определено».
3. Подходит ли наш товар-кандидат: по каждому ключевому требованию — выполняется / не выполняется / нет данных; итог.
4. Есть ли у подходящего изделия действующая регистрация в РК (реестр НЦЭЛС: https://oldregister.ndda.kz).
Если можешь искать в интернете — проверь характеристики моделей по официальным источникам и дай ссылки.
Ничего не выдумывай: нет данных — так и пиши.

Ответ — списком в формате:
Тендер № … — Лот № … — Требуется: … — ТЗ похоже на: … — Наш товар: … (подходит / не подходит: причина / нет данных) — РУ в РК: …
```

Дальше по каждому тендеру: «=== Тендер № <номер> (<площадка>) — <ссылка на объявление>»; заказчик, регион, приём до,
сумма; по каждому нашему лоту: «--- Лот № … : <название> — N шт., до … ₸ за ед.»; «Сверка АИС: <вердикт>[; ТЗ под X]»;
«Требования ТЗ (N):» списком; «Текст ТЗ:» (раздел характеристик); «Наши товары-кандидаты:» — до 3: название, ссылка на
сайт, РУ (№, «действует до … / истекло / не найдено»), характеристики с сайта, из карточки РУ — назначение и краткие
характеристики; «Похожие изделия в реестре НЦЭЛС РК:» — до 3 кандидатов подбора лота (`RegistryMatchService`, как
панель «Подбор»): наименование, производитель, страна, № РУ, краткие характеристики, если уже загружены (живых запросов
в ndda.kz при копировании нет). Поля одной строкой, без управляющих символов.

## 10. Данные (V39, только добавления)
- `product_registration` (не рыночная): `reg_number` (PK, нормализованный), `status` (ACTIVE / EXPIRED / NOT_FOUND),
  `ndda_id`, `name`, `producer`, `country`, `reg_date`, `expiration_date`, `unlimited`, `purpose`, `use_area`,
  `tech_chars`, `risk_class`, `complect` (JSONB), `checked_at`, `error`.
- `tender_lot_product_match`: `fit` (FITS / FITS_NO_RU / PARTIAL / NOT_FIT / NO_REQUIREMENTS), `fit_product_id`
  (→ `site_product`, `ON DELETE SET NULL`), `fit_met`, `fit_total`, `fit_reason` (до 300), `foreign_brand` (до 100),
  `fit_rows` (JSONB: строки сверки лучшего товара + краткие итоги вариантов), `fit_checked_at`; `level` — ещё FITS
  (`VARCHAR(10)` хватает).
- Список требований ТЗ не хранится — считается из текста при показе и при «Для ИИ».

## 11. API
- `GET /api/product-catalog` (видят все) → товары рынка: `{id, name, brand, url, regNumber, regStatus, regExpires,
  regUnlimited, attributesCount}` + `checkedAt`; `POST /api/product-catalog/refresh` (ADMIN) — каталог + РУ.
- У лота (`productMatches`) — ещё `fit`, `fitProduct {name, url, regStatus}`, `fitMet`, `fitTotal`, `fitReason`,
  `foreignBrand`, `fitRows [{mark, text, ours, source}]`, `alternatives [{productId, name, fit, met, total}]`;
  у лота без отметки с разобранным ТЗ — `requirements [{text}]`.
- `GET /api/tenders/{id}/ai-brief` → `text/plain` (один тендер); `GET /api/tenders/ai-brief?our=…&group=…` →
  `{text, tenders, total}` (тот же отбор, что фильтр «Наш товар»). Тендер другого рынка / вида — 404 (`findPublic`).

## 12. Нагрузка на goszakup
ТЗ скачиваются (очередь `ProductSpecChecker`, до 10 за прогон, сначала ближайший срок) только у лотов тендеров, где
сумма **всех отмеченных** лотов (любого уровня — ТЗ и нужно, чтобы узнать, подходит ли наш) не меньше порога
`PRODUCT_WATCH_NOTIFY_MIN_SUM` (цена за единицу × количество; лот один и без цены — сумма тендера; неизвестна — не
качаем). Проверка РУ — ndda.kz (без токена), 37 номеров раз в сутки.

## 13. Проверка качества
- **Разметка** набора (37 ТЗ + ТЗ найденных на проде 2026-10-20, обезличивать не нужно — ТЗ публичные): по лоту —
  ожидаемый вердикт и товар (FITS / PARTIAL / NOT_FIT / NO_REQUIREMENTS), чужой бренд; размечает исполнитель по
  характеристикам товаров (после внесения Фотек / Ориона), спорные — оператору.
- **Гейт** (`ProductFitQualityTest`, по образцу `ProductSpecMatchQualityTest`): ложных FITS — 0 (на ТЗ «не подходит»,
  «не наше» и под чужой бренд без нашего аналога); найдено верных FITS — не меньше порога разметки (храповик); BOWA и
  ZOLL — «ТЗ под …», NELLCOR / Valleylab / Covidien — нет.
- **Тесты** разбора требований — литералами из настоящих ТЗ (аспиратор, облучатель, ЭКГ, BOWA): склейка строк, «;» и
  столбик, условия, диапазоны, модуль вакуума, счётные без единицы, габариты, пропуск «не требований»; отметки и вердикты;
  проверка РУ на заглушке ndda (действует / истекло / не найдено / сбой); «Для ИИ» — текст, пределы, рынок; мутации.
- **Живьём:** локально (goszakup — малыми порциями, Telegram — заглушка), 1280 / 390, обе темы, оператор.

## 14. Выкладка и откат
Обычный деплой (V39 — только добавления). После старта — проверка РУ и пересчёт открытых тендеров; ставшие FITS придут
в тему 95 одним сообщением (остаток — следующими прогонами). **Откат кода ниже V39 — сначала SQL:**
`update tender_lot_product_match set level = 'TYPE' where level = 'FITS'; update tender set product_notified_level = 'TYPE'
where product_notified_level = 'FITS';` — прежний код уровня FITS не знает (DEPLOY.md §11).

## 15. Вне рамок
LLM внутри АИС; распознавание сканов ТЗ; сверка для планов закупок (нет ТЗ); рынок РФ; автоматическая запись на сайт
(только разово, после «да»); сравнение комплектности поштучно (только признаками); «Найти тендеры» в частной заявке
(как есть).

## 16. Решения при планировании
Из плана `docs/superpowers/plans/2026-10-20-product-spec-fit.md` (дословно):

1. Сверка — со **всеми** товарами группы, лучший — по вердикту (`SimilarProducts` отсекал бы родовые названия лотов: «Электрокоагулятор» по словам не похож на «ВЧ электрохирургический блок …»); варианты «ещё: …» — до 2 следующих с ✓ > 0.
2. «Обновить» на вкладке «Товары» — существующий `POST /api/site-catalog/sync` (`ProductWatchScheduler.startCatalog` теперь после каталога проверяет РУ и ставит пересчёт); отдельного `/refresh` нет.
3. «Для ИИ» списком — `POST /api/tenders/ai-brief {ids}`: отбор делает экран (тот же фильтр «Наш товар», что видит оператор), сервер проверяет рынок и вид каждого id (`findPublic`), лишние сверх 15 отбрасывает.
4. Числа — по модулю: «−80 кПа» = 80 (разрежение); температуры со знаком в требованиях редки — принято.
5. «г» без «р» / «рамм» — не граммы (путается с «2025 г.»); масса — «кг», «гр», «грамм».
6. Блок сверки и список требований в карточке тендера — standalone-компонент `LotFitComponent` под `@defer`.
7. В отметке — `fit_candidates` (JSONB): лучший товар + до 2 вариантов со строками сверки (≤ 80 строк на товар, текст ≤ 160 знаков) — переключение «ещё: …» без запроса к серверу.
8. Статус РУ товара: `ACTIVE` / `EXPIRED` / `NOT_FOUND` (в реестре нет) / `NOT_SPECIFIED` (на сайте нет №) / `UNKNOWN` (не проверено или сбой без прежних данных); не `ACTIVE` → `FITS_NO_RU` с текстом «РУ истекло / не найдено / не указано / не проверено».
9. Чужой бренд ищется в русской части ТЗ (`required_spec` хранит только её): поле «Өндіруші» казахской части недоступно — BOWA ловится по «BOWA ARC 303» (слово латиницей с кодом модели рядом).
10. В JSON сверки отметки — имена `OK` / `FAIL` / `DIFF` / `UNKNOWN`; фронт рисует ✓ / ✗ / ≈ / ?.
11. У лота в API — `fit`, `foreignBrand` и `candidates` (лучший первым, у каждого — вердикт, счёт, РУ, ссылка и строки сверки) вместо `fitProduct` / `fitMet` / `fitTotal` / `fitReason` / `fitRows` / `alternatives` спеки §11: та же информация одной формой, «ещё: …» берёт строки варианта без запроса. «Требования ТЗ» — списком строк `requirements` у каждого лота с разобранным ТЗ; экран показывает его там, где сверки нет.
12. Буфер обмена «Для ИИ» — `navigator.clipboard.write` с `ClipboardItem`, которому отдаётся обещание текста (Safari на iPhone не пускает запись после сетевого ответа, а `writeText` из нажатия получил бы текст только после запроса); нет `ClipboardItem` — `writeText`; отказ — окно с текстом «выделите и скопируйте».
13. «Лот № …» в тексте «Для ИИ» — номер лота площадки (`source_lot_code`, «87197521-ОИ2»: по нему лот ищут на портале), нет — порядковый.
14. Текст сверки (тело ТЗ или описание площадки) — один помощник `ProductMatchService.fitText` / `fitFor`: его зовут отметка, «Требования ТЗ», «Для ИИ» и гейт — качество проверяется тем же кодом, что работает (CLAUDE.md §14).
