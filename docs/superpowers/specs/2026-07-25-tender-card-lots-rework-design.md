# Переработка карточки тендера: лоты и панели лота

**Дата:** 2026-07-25
**Статус:** утверждено оператором
**Область:** только фронтенд (`frontend/src/app/pages/tenders/`). Бэкенд и API не меняются.

## 1. Мотив

Жалоба оператора: работа с лотами в карточке тендера неудобна, **на телефоне таблицу лотов приходится мотать вправо-влево**. Сейчас лоты — таблица до 10 колонок (`☐ · № · Название · Тип · Кол-во · Макс. цена · Габариты · Вес · Спецификация · Действия`), обёрнутая в `.table-scroll` (горизонтальный скролл, введён мобильным адаптивом 2026-07-15). Те же грабли — внутри панелей «Подбор» (кандидаты НЦЭЛС), «Комплектность» и «КП» (поставщики): там тоже таблицы в `.table-scroll`.

Вторая, менее заметная проблема: панели «Подбор»/«Комплектность»/«КП» рендерятся **под всем списком лотов**, а не у своего лота. Оператор жмёт «Подбор» на пятом лоте — панель появляется где-то ниже, вне контекста; на телефоне это ещё и вслепую.

Третья: `tenders.component.ts` разросся до **1943 строк** (114 kB), из них ~600 строк шаблона и ~18 kB стилей при бюджете `anyComponentStyle` 24 kB. Зона лотов — примерно половина этого объёма.

Уточнения оператора при брейншторме:
- **С телефона делается полный цикл работы** (разобрать ТЗ, подобрать из реестра, «взять в работу», отправить КП), а не только просмотр. Значит все панели должны быть полноценно рабочими на 390px.
- Объём работы — **лоты и всё, что открывается от лота**. Инфо-шапка тендера и секция «Запросы КП» в эту работу не входят.

## 2. Принятые решения

| Вопрос | Решение |
|---|---|
| Вид лота | **Лот-аккордеон на обеих ширинах**, таблицы лотов больше нет. Один код на десктоп и мобилку — как у списка тендеров (`div.tender-card`) |
| Где открываются панели | **Внутри развёрнутого лота**, а не под списком |
| Свёрнутый лот | Факты (название, кол-во, макс. цена, предложенная модель, кому ушло КП) **+ чип стадии работы по лоту** |
| Разбиение | **Три компонента**: `app-tender-lots`, `app-lot-registry-panel`, `app-lot-kp-panel` |
| Попутный фикс | Хардкод-селект «Тип оборудования» в форме лота → справочник `equipment_type` с реальным сохранением |

Отклонено осознанно: отдельный полноэкранный «экран лота» (теряется обзор соседних лотов, появляется второй уровень «назад»); сохранение таблицы на десктопе с карточками только на мобилке (двойной код и панели всё равно остаются вне контекста лота); ряд быстрых фильтров по стадии над лотами (лотов обычно 3–10, экранное место дороже).

## 3. Архитектура

Три новых standalone-компонента в `frontend/src/app/pages/tenders/`.

### 3.1 `app-tender-lots` (`tender-lots.component.ts`)

Тулбар лотов + список лотов-аккордеонов + форма добавления/редактирования лота.

```
@Input() tender: any            // нужен для isImportedTender/platform/id
@Input() lots: any[]
@Input() priceRequests: any[]   // для чипа стадии и строки «КП: …»
@Input() equipmentTypes: any[]  // справочник видов МИ (форма лота + КП-панель)
@Output() lotsChanged           // → родитель loadLots()
@Output() priceRequestsChanged  // → родитель loadPriceRequests()
@Output() bulkPriceRequested    // → родитель открывает app-bulk-price-modal
@Output() matchRequested: {lotId, lotNumber}  // → родитель открывает app-smart-match
```

Переезжает из `tenders.component`: `lotSel`/`toggleLotSel`/`allLotsSelected`/`toggleAllLots`, `toggleSpec`/`specPreview`, `openMenuLotId`/`toggleLotMenu`/`closeLotMenu` (+ `@HostListener('document:click')`), `tzBusy`/`parseTechSpec`, `clearProposed`, `kpDistributorsFor`, `lotHasCriteria`, `isImportedTender`, `showLotForm`/`editingLotId`/`lotForm`/`onAddLot`/`onEditLot`/`onSaveLot`/`onDeleteLot` и их `validationErrors` (своя копия, независимая от формы тендера).

`hasAnyType()`/`hasAnyDims()`/`hasAnyWeight()` **не переезжают — они исчезают**: правило «пусто — не рисуем» становится по-лотовым (деталь показывается, если заполнена у этого лота), а не по-колоночным.

Состояние разворота: `expandedLotId: number | null` — **развёрнут ровно один лот**. Выбор чекбоксами (`lotSel`) от разворота не зависит и при сворачивании не теряется.

`app-smart-match` остаётся у родителя (открывается поверх страницы, не привязан к месту в потоке).

### 3.2 `app-lot-registry-panel` (`lot-registry-panel.component.ts`)

Панель «Подбор»: кандидаты реестра НЦЭЛС + разворот описания карточки НЦЭЛС + блок «Комплектность аппаратов». Реестр и комплектность держим в одном компоненте: комплектность открывается кнопкой из панели реестра и работает по тому же лоту.

```
@Input() lot: any
@Input() imported: boolean   // для подсказки «нажмите ТЗ»
@Output() adopted            // «Взять в работу» → родитель lotsChanged
@Output() close
```

Переезжает: `registryPanel`/`onLotRegistry`/`closeRegistryPanel`, `toggleRegistryDetail`, `registryDetailEmpty`, `scorePct`, `adoptFromRegistry`, `adoptBusy`, `complectPanel`/`openComplect`/`runComplect`/`closeComplect`, `adoptComponent`.

### 3.3 `app-lot-kp-panel` (`lot-kp-panel.component.ts`)

Панель «КП»: вид МИ + точечный поиск (Tier 2) + список поставщиков + превью письма + отправка.

```
@Input() tenderId: number
@Input() lotIds: number[]        // один лот (внутри карточки) или несколько (из тулбара)
@Input() equipmentTypes: any[]
@Output() sent                   // → родитель loadLots() + loadPriceRequests()
@Output() close
```

Переезжает: `kpPanel`/`openKpPanel`, `changeLotType`, `researchSupplier`, `checkedSuppliers`, `sendKpRequests`, `confirmSendKp`, `cancelKpPreview`, `kpPreview`, `kpToastFromResults`. Панель сама решает **что показать** по полученным `lotIds`; **кому она принадлежит** решает `app-tender-lots` (сегодняшний `openKpPanelFor(l)` — это операция над выбором лотов, поэтому остаётся там).

**Два места рендера** (один и тот же компонент): при одном выбранном лоте — внутри развёрнутой карточки этого лота; при нескольких (кнопка «Запросить КП по выбранным (N)») — над списком лотов, потому что панель относится не к одному лоту. Режим по-прежнему определяет сервер (`singleLot` в ответе `/lot-sourcing`): селектор вида МИ и поле термина показываются только в одно-лотовом режиме.

### 3.4 Что остаётся у родителя

`tenders.component` сохраняет: список тендеров, фильтры (`app-tenders-filters`), форму тендера, инфо-шапку карточки, секцию «Запросы КП», `app-bulk-price-modal`, `app-offer-comparison`, `app-smart-match`, загрузку `lots`/`priceRequests`/`equipmentTypesList`. Ожидаемый размер после переноса — ориентировочно 1100 строк.

## 4. Раскладка лота

Одинакова на 1280px и 390px; разница только в переносе строк.

### 4.1 Свёрнутый

```
☐ №1 · Облучатель бактерицидный переносной   [● КП отправлено] ▾
   2 шт · до 450 000 ₸ · Дезинфекция
   ✅ ОБН-150 (Азовприбор) РУ ✓          ← только если есть предложенная модель
   ✉ КП: Искра Трэйдинг, MEDSYST          ← только если КП отправлены
```

Клик по шапке разворачивает; клик по чекбоксу — не разворачивает (`stopPropagation`).

### 4.2 Чип стадии

Считается на клиенте из уже загруженных `lots` + `priceRequests`, без запросов к бэкенду. Позиции лота — все `pr.items`, у которых `it.tenderLot?.id === lot.id`; «КП по лоту» — все `pr`, у которых есть такая позиция.

| Приоритет | Чип | Условие | Токен |
|---|---|---|---|
| 1 | `● Есть цены: N` | N позиций лота с непустым `it.responsePrice` | `--success` |
| 2 | `● Отказы` | КП по лоту есть, все со `status === 'DECLINED'`, цен нет | `--danger` |
| 3 | `● КП отправлено` | КП по лоту есть, цен нет | `--warn` |
| 4 | `● Модель выбрана` | `lot.proposedEquipment` | `--accent` |
| 5 | `● Есть ТЗ` | `lot.requiredSpec` | `--accent` |
| 6 | `○ Нужно ТЗ` | иначе | `--text-muted` |

Считать по **персистентному** `it.responsePrice`, не по редактируемому `it._editPrice` (последний заполняется только при разворачивании карточки КП).

Тинт — тем же приёмом, что статусы тендеров: `background: color-mix(in srgb, <токен> 15%, transparent); color: <токен>`. Тёмная тема получается автоматически.

### 4.3 Развёрнутый

Добавляются, сверху вниз:

1. **Строка деталей** — `Тип · Габариты (макс.) · Макс. вес · Бренд/модель (manufact)`. Показывается только то, что заполнено у **этого** лота; если не заполнено ничего — строки нет. Больше в `TenderLotResponse` показывать нечего: `sourceLotCode` сущность хранит, но DTO его не отдаёт, а расширять DTO — это правка бэкенда, которой в этой работе нет.
2. **Ряд действий** — `[ТЗ] [Подбор] [КП] [Подобрать] [⋯]`, условия видимости — см. §6.
3. **Аккордеон «Техническая спецификация»** — полный текст `requiredSpec`, `pre-wrap`, вертикальный скролл с ограничением высоты. Заменяет сегодняшнюю пару «колонка-превью + строка-аккордеон с colspan».
4. **Панели** `app-lot-registry-panel` / `app-lot-kp-panel` — рендерятся здесь же, если открыты для этого лота.

### 4.4 Тулбар над списком

```
[Добавить лот] [КП по всему тендеру] [Запросить КП по выбранным (N)]  ☐ выбрать все · Найдено: N лотов
```

Чекбокс «выбрать все» переезжает из шапки таблицы в тулбар с подписью. На узком экране тулбар переносится по строкам (`flex-wrap`), тач-таргеты 40px берутся из глобального `styles.scss`.

## 5. Панели: что меняется внутри

Логика подбора, матчинга и отправки переезжает **как есть** — меняется только вёрстка и место рендера.

- **Кандидаты НЦЭЛС** (`Соответствие · РУ № · Наименование · Производитель · Страна · Действует · [Взять в работу]`) — таблица → строки-карточки: заголовок = наименование, под ним `РУ № · производитель · страна · срок`, слева бейдж соответствия (процент или «✓ по названию»), справа/снизу кнопка «Взять в работу». Клик по строке по-прежнему разворачивает описание из карточки НЦЭЛС; разворот «ТЗ лота ↔ Из реестра» на узком экране становится одноколоночным.
- **Компоненты комплектности** (`Совпадение · Компонент · Тип · Страна · [Взять в работу]`) — так же в карточки; сохраняются «★ рекомендуем» на первом и сворачивание нерелевантных (`0%`) под «ещё N».
- **Поставщики в панели КП** (`☐ · Поставщик · Email · Почему`) — в карточки: чекбокс + имя (ссылка на сайт, если есть), под ним email (с пометкой «письмо не уйдёт» при пустом) и чипы причин; сохраняются подсветка лучшего, преотметка сильнейших и сворачивание нерелевантных.
- **Превью письма** остаётся модалкой поверх (уже адаптивна: `width: min(720px, 92vw)`).

После переработки `.table-scroll` в зоне лотов не должно остаться ни одного.

## 6. Инварианты, которые нельзя потерять при переносе

Это существующее поведение; при переезде оно должно сохраниться дословно.

- «ТЗ» — только на импортных тендерах (`isImportedTender()`), с блокировкой на время разбора (`tzBusy`).
- «Подбор» (реестр НЦЭЛС + комплектность) — только рынок KZ.
- «Подобрать» (каталог-матч, `app-smart-match`) — только РФ **и** `lotHasCriteria(l)`.
- «КП по всему тендеру» — только на ручных тендерах (`!isImportedTender()`).
- «Запросить КП по выбранным» — заблокирована при пустом выборе.
- Смена вида МИ в панели КП сохраняется на сервер и пересобирает подбор (`setLotEquipmentType` → `loadLots` + переоткрытие панели).
- Токен `[КП-id]` в теме письма — серверный; правки темы в превью не должны его подставлять.
- «Взять в работу» (реестр и комплектность) — разные эндпоинты (`adopt-registry` / `adopt-component`), обе блокируются общим `adoptBusy`.
- Ручное снятие предложенной модели (`✕` у строки «Предложено»).
- После async-операций компоненты руками зовут `cdr.detectChanges()` — как в остальном коде.

## 7. Попутный фикс: селект типа оборудования в форме лота

Дефект из бэклога (CLAUDE.md §16), живёт ровно в переносимом коде: форма лота содержит `<select formControlName="equipType">` с четырьмя зашитыми строками (`УЗИ/Рентген/ИВЛ/Монитор`), а API ждёт `equipTypeId` — выбранный тип молча не сохраняется.

Чиним при переносе: селект наполняется из `@Input() equipmentTypes` (справочник `equipment_type`, 18 типов), поле формы становится `equipTypeId`, при редактировании подставляется `lot.equipmentType?.id`, в запрос уходит `equipTypeId`. Пустое значение (`— не выбран —`) шлёт `null`.

## 8. Стили и тёмная тема

- Новые компоненты сразу на **токенах** (`--surface`, `--surface-2`, `--border`, `--text`, `--text-muted`, `--accent`, `--success`, `--warn`, `--danger`, `--shadow`), без хексов. Фикс-цветные кнопки, читаемые в обеих темах (зелёная «КП», индиго «ТЗ»), допустимы — как решено при вводе тёмной темы.
- `@media`-блоки — **только в конце** блока `styles` (гоча CLAUDE.md §14: при равной специфичности позднее базовое правило молча перебивает более раннюю @media-переопределялку).
- Grid не задавать через `repeat(N, 1fr)` там, где содержимое может не сжаться ниже min-content.
- Бюджет `anyComponentStyle` (24 kB) — у каждого компонента свой; `tenders.component` при этом разгружается с сегодняшних ~18 kB.

## 9. Риски

| Риск | Митигация |
|---|---|
| Тендер с 20+ лотами станет длиннее, чем таблица | Свёрнутый лот — 2–4 компактные строки; развёрнут всегда один |
| Регресс поведения при переносе ~500 строк логики | §6 — чеклист инвариантов; перенос без правок семантики; живая проверка каждого потока |
| Потеря выбранных лотов при сворачивании | `lotSel` независим от `expandedLotId` |
| Десктопный оператор привык к таблице | Свёрнутый вид даёт те же ключевые поля плюс стадию; глубокие поля (габариты/вес/тип) и так были пустыми у большинства импортных лотов |

## 10. Проверка

Гейт сборки: `cd frontend && npm run build` — зелёный (включая бюджеты).

Живая проверка Playwright на реальном KZ-тендере с лотами, **1280px и 390px × светлая и тёмная тема**:

1. Список лотов: свёрнутый вид, чипы стадий на лотах в разных состояниях (без ТЗ / с ТЗ / с моделью / с отправленным КП / с ценами).
2. Разворот лота: детали, действия, аккордеон спецификации.
3. «ТЗ» на импортном лоте → спецификация появляется, чип стадии меняется.
4. «Подбор»: кандидаты НЦЭЛС → разворот описания НЦЭЛС → «Комплектность аппаратов» → «Взять в работу» → на лоте появляется предложенная модель.
5. «КП» на одном лоте: вид МИ, точечный поиск, отметка поставщиков, превью письма, отправка → чип стадии становится «КП отправлено».
6. Мульти-выбор лотов → «Запросить КП по выбранным (N)» → панель над списком.
7. Форма лота: добавление и редактирование, **выбранный тип оборудования сохраняется** (проверить перезагрузкой).
8. Рынок РФ: «Подобрать» открывает smart-match; «Подбор» отсутствует; «КП по всему тендеру» доступна на ручном тендере.
9. Отсутствие регресса: инфо-шапка тендера, секция «Запросы КП», сравнение предложений.
