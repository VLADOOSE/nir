# Вход по Face ID / Touch ID (passkeys) для АИС — дизайн

**Дата:** 2026-09-28
**Статус:** утверждён оператором (части 1–3 согласованы в чате 2026-09-28); уточнения после сверки с исходниками Spring — §1.1, их оператор видит впервые в этой спеке
**Контекст:** следом за калиткой по коду устройства (`2026-09-28-device-gate-design.md`, в проде с 2026-09-28): до страницы входа `https://ais.westmed.kz` доходят только допущенные устройства, а дальше — логин и длинный пароль. CLAUDE.md §5 (прод; push делает оператор), §6 (архитектура), §12 (UI-kit, мобильная вёрстка, тёмная тема), §14 (уроки).
**Запрос оператора:** «при следующем входе с айфона он также потребует логин admin и тот длинный пароль? может можно интегрировать биометрию? Face ID и на маке Touch ID». И отдельно: VPN с разными странами не должен заставлять заново допускать устройство.

## 1. Решения, принятые в обсуждении

| # | Вопрос | Решение |
|---|---|---|
| 1 | Способ | **Полноценные passkeys (WebAuthn).** Отвергнуто «сохранённые пароли + запомнить меня»: пароль остаётся секретом, который можно подсмотреть и ввести на поддельной странице, а ключ привязан к домену и в поддельной странице не сработает |
| 2 | Чья учётка | **Личная учётка оператора** (`vlad`, роль ADMIN): ключ принадлежит человеку, в «Устройствах» и прочих журналах видно, кто действовал. Общий `admin` остаётся запасным входом по паролю |
| 3 | Срок входа | **«Рабочий день» — 12 часов** (было: 30 минут бездействия) |
| 4 | Реализация | **Встроенная поддержка passkeys в Spring Security 6.5.5** (`http.webAuthn()`) — своя криптография и сторонние сервисы не нужны |
| 5 | VPN | **Не влияет.** Допуск калитки привязан к ключу в cookie, ключ входа — к домену и устройству; IP и страна не участвуют нигде |
| 6 | Где работает | Только на `https://ais.westmed.kz` (и `http://localhost:4200` в разработке): ключ навсегда привязан к одному домену. Tailscale и SSH-туннель — вход по паролю, как сейчас |
| 7 | Пароль | **Остаётся всегда.** Ключ — второй способ войти, а не замена |

### 1.1. Уточнения после сверки с исходниками Spring 6.5.5

Классы `spring-security-web/config` 6.5.5 разобраны `javap`; в чате этого не было:

1. **Версия webauthn4j — 0.29.5.RELEASE**, а не 0.29.7 из примера в документации Spring: именно с 0.29.5 собран и протестирован Spring Security 6.5.5 (`gradle/libs.versions.toml` тега `6.5.5`).
2. **Встроенное удаление ключа закрыто.** `DELETE /webauthn/register/{id}` в Spring удаляет ключ по id, **не проверяя ни владельца, ни даже вход** (`removeCredential` → `userCredentials.delete(id)` → 204), а фильтр стоит после проверки прав, так что при нашем `anyRequest().permitAll()` удалять ключи смог бы кто угодно. Поэтому удаление идёт только через наш `/api/passkeys/{id}` с проверкой владельца (§5.2).
3. **Ключи привязаны к учётке внешними ключами с каскадом** (§4). Spring ищет владельца ключа по **логину**, а логин в «Пользователях» редактируется. Без привязки ключи удалённой учётки достались бы новой учётке с тем же логином.
4. **Id сессии меняется при каждом входе** — и паролем, и ключом (§5.3). Spring при входе по ключу его не меняет, наш вход паролем — тоже.
5. Публичный эндпоинт — `GET /api/auth/passkey-config` и отдаёт только `rpId`. В чате было `/api/auth/passkeys` с полем `enabled`, но выключателя нет: пароль работает всегда, а кнопка ключа показывается только там, где ключ может сработать.
6. Подпись ключа по умолчанию («iPhone · Safari») берётся из того же `UserAgentSummary`, что у калитки: разбор `User-Agent` один на всю систему.
7. **Параметры регистрации без входа Spring отвечает 400, а не 401** (`sipush 400` в `PublicKeyCredentialCreationOptionsFilter`), и общий интерсептор фронта его не узнает. Поэтому фронт сам трактует этот 400 как «сессия истекла» (§7.1).

## 2. Как это работает для людей

**Добавить ключ** (один раз на устройстве): войти паролем → «Мой профиль» → поле «Подпись» (уже заполнено: «iPhone · Safari») → «Добавить вход по Face ID / Touch ID» → система спрашивает Face ID → ключ появляется в списке.

**Входить:** на странице входа — «Войти с Face ID / Touch ID» → Face ID → внутри. Логин вводить не нужно: устройство само предлагает ключи, сохранённые для АИС.

**Mac и iPhone:** ключ, созданный на iPhone, связка ключей iCloud сама переносит на Mac с тем же Apple ID — на Mac его может не понадобиться добавлять вовсе. Chrome на Mac умеет брать ключи из iCloud, а если ключа рядом нет, предлагает войти телефоном: QR-код → Face ID на iPhone → вход на Mac.

**Сколько живёт вход:** до 12 часов с момента входа. Закрыл браузер или перезагрузил телефон — всё ещё внутри; на следующий день — снова одно касание. После каждого деплоя сессии сбрасываются (они живут в памяти бэкенда) — тоже одно касание.

**Калитка остаётся:** до страницы входа по-прежнему доходит только допущенное устройство. Ключ заменяет длинный пароль, а не калитку: барьеров по-прежнему два.

**Потерян телефон:** с другого устройства — «Мой профиль» → удалить ключ телефона; админ — «Устройства» → отозвать телефон. Биометрия никогда не покидает устройство и на сервер не попадает; без Face ID или кода разблокировки телефона ключ не сработает.

## 3. Архитектура

```
Добавление ключа (вход уже выполнен):
  браузер ─POST /webauthn/register/options──▶ Spring: параметры + одноразовый вызов (challenge) → в сессию
          ◀── {rp, user, challenge, excludeCredentials, …}
```

## 4. Данные — миграция `V20__passkeys.sql`

```sql
-- Хранилище ключей входа — схема Spring Security 6.5.5 без изменений колонок
-- (user-entities-schema.sql и user-credentials-schema-postgres.sql из spring-security-web):
-- её читают и пишут JdbcPublicKeyCredentialUserEntityRepository и JdbcUserCredentialRepository.
CREATE TABLE user_entities (
    id           VARCHAR(1000) NOT NULL,   -- случайный id пользователя WebAuthn (base64url), не user_account.id
    name         VARCHAR(100)  NOT NULL,   -- логин = user_account.username
    display_name VARCHAR(200),
    PRIMARY KEY (id)
);
CREATE TABLE user_credentials (
    credential_id                VARCHAR(1000) NOT NULL,   -- id ключа (base64url)
    user_entity_user_id          VARCHAR(1000) NOT NULL,
    public_key                   BYTEA         NOT NULL,   -- ОТКРЫТЫЙ ключ; закрытый не покидает устройство
    signature_count              BIGINT,
    uv_initialized               BOOLEAN,
    backup_eligible              BOOLEAN       NOT NULL,
    authenticator_transports     VARCHAR(1000),
    public_key_credential_type   VARCHAR(100),
    backup_state                 BOOLEAN       NOT NULL,
    attestation_object           BYTEA,
    attestation_client_data_json BYTEA,
    created                      TIMESTAMP,
    last_used                    TIMESTAMP,
    label                        VARCHAR(1000) NOT NULL,   -- подпись («iPhone · Safari»)
    PRIMARY KEY (credential_id)
);

-- Наше дополнение: ключи намертво привязаны к учётке
ALTER TABLE user_entities ADD CONSTRAINT uq_user_entities_name UNIQUE (name);
ALTER TABLE user_entities ADD CONSTRAINT fk_user_entities_account
    FOREIGN KEY (name) REFERENCES user_account (username) ON UPDATE CASCADE ON DELETE CASCADE;
ALTER TABLE user_credentials ADD CONSTRAINT fk_user_credentials_entity
    FOREIGN KEY (user_entity_user_id) REFERENCES user_entities (id) ON DELETE CASCADE;
CREATE INDEX idx_user_credentials_entity ON user_credentials (user_entity_user_id);
```

- **Каскад по логину.** Spring находит владельца ключа по `user_entities.name` и грузит пользователя через `CustomUserDetailsService` по этому имени, а логин в «Пользователях» редактируется (`PUT /api/users/{id}` меняет `username`). Без каскада переименованная учётка теряла бы вход по ключу. Хуже другое: удалили `vlad`, потом завели `vlad` другому человеку — и старые ключи входили бы под новой учёткой. Внешний ключ с `ON UPDATE CASCADE ON DELETE CASCADE` закрывает оба случая в самой БД, то есть при любом способе правки учётки — через интерфейс или SQL.
- **`UNIQUE (name)`.** Запись пользователя WebAuthn Spring создаёт при первом запросе параметров регистрации. Два одновременных первых запроса создали бы две записи с одним логином, и ключи разъехались бы по ним. `user_account.username` уже `UNIQUE`, так что связь один к одному.
- Таблицы **общие, без рынка** — как `user_account` и `trusted_device`: вход не зависит от переключателя РФ/KZ.
- Типы колонок — ровно как у Spring (`TIMESTAMP` без зоны тоже): хранилища Spring пишут и читают их сами, а «улучшения» здесь — источник расхождений.

## 5. Бэкенд

### 5.1. Включение passkeys

```java
http.webAuthn(w -> w
        .rpName("АИС Медзакупки")                   // нейтральный бренд продукта (CLAUDE.md §12)
        .rpId(props.rpId())                         // ais.westmed.kz | localhost
        .allowedOrigins(props.allowedOrigins())     // https://ais.westmed.kz | http://localhost:4200
        .disableDefaultRegistrationPage(true));     // своя страница — «Мой профиль»
```

```yaml
# application.yaml (разработка)
passkeys:
  rp-id: localhost
  allowed-origins: http://localhost:4200

# application-prod.yaml
passkeys:
  rp-id: ais.westmed.kz
  allowed-origins: https://ais.westmed.kz
```

Бины `JdbcPublicKeyCredentialUserEntityRepository` и `JdbcUserCredentialRepository` (на общем `JdbcTemplate`) Spring находит в контексте сам. Без них он хранит ключи в памяти и теряет их при каждом рестарте. Профиль `prod` на сервере уже включён (`SPRING_PROFILES_ACTIVE: prod` в `docker-compose.yml`), поэтому `.env` менять не нужно.

**Что делает Spring** (сверено с классами 6.5.5):

- `POST /webauthn/register/options` — только для вошедшего; анониму — **400** (фильтр стоит до проверки прав и отвечает сам, §1.1 п. 7). При первом вызове создаёт запись пользователя WebAuthn. Параметры:
  - `residentKey: required` — ключ «находимый», при входе логин не нужен;
  - `userVerification: preferred`;
  - `attestation: none`;
  - алгоритмы ES256, EdDSA и RS256;
  - 5 минут на церемонию;
  - `excludeCredentials` — уже имеющиеся ключи пользователя, так что второй ключ на то же устройство откажет само устройство.

  Параметры кладёт в сессию.
- `POST /webauthn/register` — сверяет ответ устройства с параметрами из сессии и сохраняет ключ с подписью → `{success:true}`.
- `POST /webauthn/authenticate/options` — вызов в сессию; для анонима `allowCredentials` пуст, устройство предлагает свои ключи для домена.
- `POST /login/webauthn`:
  1. параметры берёт из сессии и сразу удаляет, так что вызов одноразовый;
  2. проверяет подпись и обновляет `last_used` и счётчик;
  3. грузит пользователя через `CustomUserDetailsService`, роль при этом берётся свежая из БД;
  4. кладёт вход в сессию → `{authenticated:true, redirectUrl}`.

  Отказ → 401 без тела.
- `DELETE /webauthn/register/{id}` — удаляет без проверок, закрыт (§5.2).
- **Принципал после входа по ключу — `PublicKeyCredentialUserEntity`, а не `UserDetails`**; `getName()` = логин. Наш код берёт пользователя только через `getName()` (`AuthController.me`, `DeviceController`, `LeadController`), так что всё совместимо. Новый код не должен приводить принципал к `UserDetails`.
- Apple-устройства при `preferred` всегда спрашивают Face ID / Touch ID или код устройства. Требовать `required` на сервере не нужно (§12).

### 5.2. Правила доступа

`SecurityConfig`, порядок важен — побеждает первое совпадение:

```java
.requestMatchers(HttpMethod.DELETE, "/webauthn/**").denyAll()       // встроенное удаление — никому (§1.1 п. 2)
.requestMatchers("/webauthn/register", "/webauthn/register/**").authenticated()
.requestMatchers("/api/auth/**").permitAll()                        // дальше — как сейчас
…
```

Параметры и вход (`/webauthn/*/options`, `/login/webauthn`) Spring обрабатывает фильтрами **до** проверки прав, поэтому правила их не касаются: вход, конечно, доступен анониму. Регистрация стоит после проверки прав, её и закрывает `authenticated()`.

**Фронт-контейнер** (`frontend/nginx.conf`) пропускает к бэкенду ровно четыре пути и только методом POST:

```nginx
# passkeys: встроенные эндпоинты Spring Security живут вне /api. Только точные пути и только POST:
# встроенное удаление ключа (DELETE /webauthn/register/{id}) наружу не выходит вовсе.
location ~ ^/(login/webauthn|webauthn/authenticate/options|webauthn/register/options|webauthn/register)$ {
    limit_except POST { deny all; }
    proxy_pass http://ais-backend:8080;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}
```

Удаление закрыто трижды: nginx не пропускает, Spring отвечает `denyAll`, а единственный рабочий путь — `/api/passkeys/{id}` с проверкой владельца.

### 5.3. Сессия

- `server.servlet.session.timeout: 12h` и `server.servlet.session.cookie.max-age: 12h`. Вход живёт до 12 часов с момента входа и переживает закрытие браузера и перезагрузку телефона; 12 часов без действий — тоже выход. Было: 30 минут бездействия (умолчание Spring Boot) и cookie до закрытия браузера.
- **Id сессии меняется при каждом успешном входе:**
  - паролем — `AuthController.login` вызывает `request.changeSessionId()`, если сессия уже была;
  - ключом — `SessionIdRotationFilter` стоит перед фильтром входа по ключу и на `POST /login/webauthn` при существующей сессии делает то же.

  Зачем: сессия, открытая до входа, могла быть подсунута — например, cookie `JSESSIONID` на весь домен с другого сайта `*.westmed.kz`. После входа такой id ничего не стоит. Смена id сохраняет содержимое сессии (включая параметры входа по ключу) и заново выдаёт cookie со свежими 12 часами. Калитка этот путь уже закрывает: чужой браузер до АИС не доходит и id сессии получить не может. Это второй слой, и он дешёвый.

### 5.4. Свои ключи — `PasskeyService`

- **Список:** `findByUsername(логин)` → `findByUserId(id)` → подпись, когда добавлен, когда последний вход. Ключей нет → пустой список.
- **Удаление:** ключ по id. Если его нет, он чужой или id битый — 404, одинаково, чтобы по ответу нельзя было узнать, существует ли чужой ключ. Свой → удалить → 204.
- `suggestedLabel` — `UserAgentSummary.describe(User-Agent)`: «iPhone · Safari», «Mac · Chrome», нераспознанное — «Браузер».

## 6. API

**Наши эндпоинты:**

| Метод | Путь | Доступ | Ответ |
|---|---|---|---|
| GET | `/api/auth/passkey-config` | все (`/api/auth/**`) | `{rpId}` — фронт показывает кнопку только если `location.hostname === rpId` |
| GET | `/api/passkeys` | вошедший | `{keys:[{id, label, createdAt, lastUsedAt}], suggestedLabel}` — только свои ключи |
| DELETE | `/api/passkeys/{id}` | вошедший | 204 — свой ключ удалён; 404 — нет такого, чужой или битый id |

**Встроенные эндпоинты Spring — это контракт с фронтом.** Форматы ровно как у эталонного клиента Spring (`spring-security-webauthn.js` из `spring-security-web-6.5.5.jar`); двоичные поля — base64url без `=`:

| Метод | Путь | Тело запроса | Ответ |
|---|---|---|---|
| POST | `/webauthn/register/options` | — | параметры создания: `challenge`, `user.id` и `excludeCredentials[].id` — base64url, фронт декодирует их в `ArrayBuffer` |
| POST | `/webauthn/register` | `{publicKey:{credential:{id, rawId, response:{attestationObject, clientDataJSON, transports}, type, clientExtensionResults, authenticatorAttachment}, label}}` | `{success:true}` |
| POST | `/webauthn/authenticate/options` | — | параметры входа: `challenge`, `allowCredentials[].id` — base64url |
| POST | `/login/webauthn` | `{id, rawId, response:{authenticatorData, clientDataJSON, signature, userHandle}, credType, clientExtensionResults, authenticatorAttachment}` | `{authenticated:true, redirectUrl}`; отказ — 401 |

При входе поле называется `credType`, а не `type`, — так шлёт эталонный клиент Spring, повторяем как есть. `redirectUrl` фронт игнорирует: после входа — `/dashboard`, как при входе паролем.

## 7. Фронт

### 7.1. `PasskeyService`

- `usableHere(rpId)` — есть `window.PublicKeyCredential` **и** `location.hostname === rpId`. На Tailscale, SSH-туннеле и в браузерах без WebAuthn — `false`.
- `login()` — параметры → `navigator.credentials.get` → `POST /login/webauthn`.
- `register(label)` — параметры → `navigator.credentials.create` → `POST /webauthn/register`.
- base64url-кодирование и сборка тел — как в эталонном клиенте Spring (§6).
- Запросы идут через `HttpClient`: работают общие интерсепторы, в том числе уход на калитку по `X-AIS-Gate`.
- **Safari и «жест пользователя».** С iOS 17.4 / macOS 14.4 Safari вызывает WebAuthn без требований к жесту. На более старых допускается один сетевой запрос между нажатием и вызовом — так и устроено: нажатие → запрос параметров → вызов.
- **Ошибки сервис сводит к четырём исходам:**
  - `cancelled` — `NotAllowedError`/`AbortError`: отмена, закрытое окно, ключа нет;
  - `exists` — `InvalidStateError` при добавлении: ключ на этом устройстве уже есть;
  - `rejected` — сервер не принял ключ при входе (401 от `/login/webauthn`);
  - `session` — при добавлении сессии уже нет: 400 от `/webauthn/register/options` (§1.1 п. 7) или 401 от `/webauthn/register`;
  - `failed` — всё прочее.

  Как их показать — дело экрана (§8).

### 7.2. Страница входа

- Под формой пароля — разделитель «или» и кнопка **«Войти с Face ID / Touch ID»** (контурная, во всю ширину, иконка — инлайн-SVG: lucide на экране входа не используем, CLAUDE.md §14).
- Кнопка появляется, только если `usableHere(rpId)` (rpId — из `/api/auth/passkey-config`). Пока идёт вход — кнопка заблокирована, на ней «Ждём Face ID / Touch ID…».
- Успех → `auth.loadCurrentUser()` (`/api/auth/me`) → `/dashboard`.
- Полям логина и пароля — `name` и `autocomplete="username"` / `autocomplete="current-password"`: менеджеры паролей сохранят запасной пароль (например, общего `admin`).

### 7.3. «Мой профиль» (`/profile`)

- Маршрут под `authGuard` — доступен всем, не только ADMIN. Пункт «Мой профиль» — в группе «Система» перед «О системе»; имя пользователя в шапке тоже ведёт на профиль (на мобилке имя скрыто, остаётся пункт меню).
- **Учётная запись:** ФИО, логин, роль.
- **«Вход по Face ID / Touch ID»:**
  - список ключей — подпись, «добавлен 28.09.2026», «последний вход: сегодня 10:42» или «ещё не использовался», кнопка «Удалить» с подтверждением через `ConfirmService`;
  - пустой список — «Ключей пока нет. Добавьте — и входите без пароля»;
  - добавление: поле «Подпись» (1–60 символов, по умолчанию `suggestedLabel`) + кнопка «Добавить вход по Face ID / Touch ID»; успех → тост и обновлённый список. Длину проверяет фронт. Регистрацию принимает фильтр Spring, своего валидатора на сервере нет: подпись вводит владелец для собственного ключа, а колонка держит до 1000 символов.
- **Где добавить нельзя:**
  - хост не совпал с rpId (Tailscale, туннель) — вместо кнопки: «Добавить ключ можно на https://ais.westmed.kz»;
  - браузер без WebAuthn — «Этот браузер не поддерживает вход по ключу».

  Список и удаление работают везде.
- Текст подтверждения удаления: «Удалить ключ «iPhone · Safari»? Войти с ним больше не получится. Сам ключ останется в связке ключей устройства — его можно удалить в настройках паролей».
- UI-kit проекта (CLAUDE.md §12): токены, светлая и тёмная тема, мобильная раскладка ≤900px, тач-таргеты, `@media` в конце стилей.

### 7.4. Прочее

- `authInterceptor`: условие «401 → logout + `/login`» не срабатывает для `/login/webauthn` (как уже не срабатывает для `/api/auth/`). Отказ в ключе — не «сессия истекла», и страница входа сама скажет, что случилось. Ветка калитки (`X-AIS-Gate`) — первой, для всех запросов, как сейчас.
- `proxy.conf.json` (разработка): `/webauthn` и `/login/webauthn` → `http://localhost:8080`.

## 8. Ошибки и крайние случаи

| Ситуация | Что видит человек |
|---|---|
| Нажал «Войти с Face ID» и отменил | Ничего: кнопка снова активна |
| Ключа для АИС на устройстве нет | Системное окно предлагает войти телефоном по QR-коду; если закрыть — неброская подсказка под кнопкой: «Не получилось войти по ключу. Если ключа на этом устройстве ещё нет — войдите паролем и добавьте его в «Мой профиль»». Отмену и «ключа нет» браузер не различает (оба — `NotAllowedError`), поэтому текст один и мягкий |
| Ключ удалён в АИС, но остался в связке ключей устройства | Устройство подписывает, сервер отвечает 401 → «Ключ не принят. Попробуйте ещё раз; если не получится — войдите паролем и добавьте ключ заново в «Мой профиль», а старый удалите в настройках паролей устройства». Текст один на любой отказ сервера: 401 без тела не говорит, удалён ключ или просто сбились параметры входа (две вкладки, деплой между шагами), а уверенное «ключ удалён» было бы враньём в половине случаев |
| Учётку удалили или переименовали | Удаление — ключи уходят вместе с ней (каскад, §4) → как строкой выше. Переименование — ключи продолжают работать под новым логином |
| Добавляет ключ, который на этом устройстве уже есть | «На этом устройстве ключ для вашей учётки уже есть» |
| Сессия истекла, пока добавлял ключ | Как везде: выход и страница входа. 401 от `/webauthn/register` ловит общий интерсептор, а 400 от параметров регистрации — сам экран профиля (исход `session`) |
| Устройство не допущено калиткой или отозвано | 401 с `X-AIS-Gate` → `/gate/` (интерсептор, как сейчас) |
| Tailscale, SSH-туннель, другой хост | Кнопки нет, вход паролем. В профиле — подсказка, где добавить ключ |
| Браузер без WebAuthn или старый Safari | Кнопки нет либо мягкая подсказка при неудаче; пароль работает |
| Вход по ключу начат в двух вкладках | Параметры в сессии одни: вторая вкладка перезапишет первую, первая получит 401 → «ключ не принят», повтор проходит |
| Потерян телефон | С другого устройства: «Мой профиль» → удалить ключ телефона. Админ: «Устройства» → отозвать телефон |

## 9. Безопасность

- **Ключ не выманить поддельной страницей.** Он привязан к домену `ais.westmed.kz`: браузер не отдаст подпись другому сайту, даже похожему.
- **Утечка базы не даёт входа.** Сервер хранит только открытые ключи, а подпись без закрытого ключа не подделать.
- **Биометрия остаётся на устройстве.** АИС получает только подпись; Face ID / Touch ID — забота iOS и macOS.
- **Два барьера:** калитка (допущенное устройство), затем ключ или пароль учётки. Ключ калитку не обходит — его пути идут через `location /` под `auth_request`.
- **Удаление ключей — только своих** (§5.2), трижды закрыто.
- **Регистрация — только себе и только после входа.** Параметры регистрации Spring привязывает к пользователю сессии, и регистрационный запрос сверяется с ними.
- **Ключи не переходят к новой учётке со старым логином** (§4).
- **Id сессии меняется при входе** (§5.3).
- **Перебор бессмыслен:** угадать подпись нельзя, поэтому отдельного лимита на `/login/webauthn` нет. Общий лимит хоста — 10 запросов в секунду с IP; `/api/auth/login` сохраняет свой.

## 10. Раскатка

1. **Код.** Мерж → оператор делает push (`! git push origin main`, CLAUDE.md §5) → деплой: Flyway накатит V20, образ фронта принесёт новый `nginx.conf`. nginx хоста не трогаем. Деплой сбросит сессии — войти заново.
2. **Проверка на сервере** (через SSH-туннель `http://localhost:8090`, с согласия оператора):
   - бэкенд жив, Flyway V=20;
   - `GET /api/auth/passkey-config` → `{"rpId":"ais.westmed.kz"}`;
   - `POST /webauthn/register/options` без входа → 400;
   - `DELETE /webauthn/register/x` → до бэкенда не доходит: путь не проксируется, nginx фронта отвечает сам (405).
3. **Учётка `vlad`** (ADMIN, «Владислав Ширяев»). Заводит оператор в «Пользователях» или агент по API с согласия. Пароль генерируется в `~/.config/ais/ais-vlad.pass` (права 600, не печатается; копировать — `pbcopy < ~/.config/ais/ais-vlad.pass`); он остаётся запасным входом.
4. **iPhone:** `ais.westmed.kz` → вход `vlad` паролем → «Мой профиль» → «Добавить вход по Face ID» → «Выйти» → «Войти с Face ID» → внутри. Проверяем: в списке ключа появился «последний вход».
5. **Mac:** «Войти с Face ID / Touch ID». Если ключ из iCloud не предложен — войти паролем и добавить ключ Touch ID.
6. **Запасной вход:** общий `admin` по паролю работает как прежде; на Tailscale кнопки нет, пароль работает.
7. **Откат:** revert мерж-коммита + push. Вход паролем раскаткой не затрагивается ни на одном шаге. Таблицы V20 останутся пустым грузом (Flyway не откатывает), ключи на устройствах станут бесполезны — удалить в настройках паролей.

## 11. Тестирование

- **Бэкенд** (`@SpringBootTest @Transactional` на nirdb; MockMvc собирается из общего контекста с `springSecurity()`, без `@AutoConfigureMockMvc` — урок калитки: лишний контекст упирает набор в `max_connections`):
  - **Полный цикл на эмуляторе ключа.** Тестовый помощник на самом webauthn4j-core и JDK: ES256, аттестация `none`, `clientDataJSON` с origin `http://localhost:4200`. Новых тестовых зависимостей нет — `webauthn4j-test` тянет BouncyCastle и ещё три модуля. Цикл: вход паролем → параметры регистрации → регистрация → выход → параметры входа → вход по ключу → `/api/auth/me` в той же сессии = наш пользователь, `last_used` проставлен;
  - **отказы входа:** подпись чужим ключом → 401; удалённый ключ → 401; origin `https://evil.example` в `clientDataJSON` → 401; повтор того же ответа (вызов уже израсходован) → 401;
  - **правила доступа:**
    - без входа: `POST /webauthn/register/options` → 400, `POST /webauthn/register` → 401;
    - `DELETE /webauthn/register/{id}` без входа и со входом → 403, ключ на месте;
    - `/api/passkeys` без входа → 401;
  - **только свои:** список — только свои ключи; удаление чужого → 404 и ключ на месте; своего → 204;
  - **привязка к учётке:** переименование — ключ входит под новым логином; удаление учётки — ключей нет; новая учётка со старым логином ключей не получает;
  - **сессия:** id меняется при входе паролем и при входе ключом; старый id после входа не авторизован;
  - `/api/auth/passkey-config` отдаёт rpId из конфига; `suggestedLabel` — из `User-Agent`;
  - **гарды — прогон мутациями** (CLAUDE.md §14; по одной, с проверкой, что краснеет ровно свой тест): снять `denyAll`; снять проверку владельца; снять каскад (внутри транзакции теста); убрать смену id сессии.
- **Весь набор:** `./gradlew cleanTest test` — 0 падений.
- **Фронт:** `npm run build`. Вживую в Playwright с виртуальным аутентификатором Chrome (CDP `WebAuthn.addVirtualAuthenticator`: `internal`, `hasResidentKey`, `isUserVerified`) на `http://localhost:4200`, 1280 и 390, светлая и тёмная тема:
  - добавить ключ → выйти → войти ключом → удалить ключ → вход ключом даёт «Ключ не принят…»;
  - отмена — тихо;
  - на `http://127.0.0.1:4200` (хост ≠ rpId) кнопки нет.
- **Прод:** настоящие Face ID на iPhone и Touch ID на Mac (§10, шаги 4–6).

## 12. Вне этого этапа

- Подсказка ключа прямо в поле логина (conditional UI, `autocomplete="username webauthn"`) и автопоказ Face ID при открытии страницы входа.
- Управление чужими ключами из «Пользователей» (сброс ключей сотрудника). Сейчас сотрудник удаляет свои сам, удаление учётки удаляет их все, а потерянный телефон дополнительно отзывается в калитке.
- Переименование ключей, смена своего пароля в профиле.
- Обязательный ключ или запрет пароля для учётки; требование `userVerification: required`.
- Сессии, переживающие деплой (spring-session-jdbc), и токены «запомнить меня».
- Signal API — чтобы устройство само забывало удалённые в АИС ключи.
- Вход ключом на хосте Tailscale (Related Origin Requests).
- Журнал входов.
