# Единая страница сделки — дизайн

**Дата:** 2026-10-18. **Статус:** дизайн согласован с оператором в разговоре по частям, спека ждёт его ревью.

**Подпроект 2 из 4 «Жизненный цикл сделки»** (CLAUDE.md §16, первый пункт). Порядок согласован 2026-10-16:
1. **Переходы между страницами** — сделаны на ветке `feature/cross-links` (ревью пройдено, исправления и слияние — впереди). Этот подпроект строится поверх неё: гард рынка у `GET /api/tenders/{id}`, карточка тендера в адресе (`?openId=`), ссылки «Переписка» и «Заявка ЧЗ-…».
2. **Единая страница сделки** — этот документ.
3. **Частники после КП:** договор → оплата клиента → заказ и оплата поставщику → поставка → закрывающие документы; «Приложить готовое КП» с записью цен.
4. **Тендеры после подачи заявки:** итог, договор, поставка, оплата — удобное ведение того, что сейчас хранится в заявке на участие.

## 1. Зачем

Слова оператора (2026-10-16): «есть обращения, есть частная заявка, КП клиенту — и можно запутаться, хорошо бы единую страницу тоже иметь, чтоб там по всему циклу двигаться… и с тендерами не забыть тоже подобное сделать».

Что значит «получилось»:
- открыл сделку — видно, на каком она этапе и что делать дальше, а следующее действие делается одной кнопкой;
- переписка с клиентом и история сделки — на той же странице, рядом с позициями, ценами и КП;
- у тендера — то же самое на его карточке.

Работают оператор и отец, позже менеджеры; с компьютера и с телефона. Записи — только админ, оператор всё видит (как везде в АИС).

## 2. Решения разговора

| # | Вопрос | Решение |
|---|---|---|
| 1 | С какого момента начинается сделка | С частной заявки. Обращение остаётся входящим ящиком: пришло → разобрались → «Создать заявку». Обращение без заявки живёт в своей карточке, как сейчас. |
| 2 | Где переписка с клиентом | Колонкой справа на широком экране (сворачивается); на узком — вкладки «Сделка \| Переписка». |
| 3 | Откуда события ленты | Смешанно: всё, у чего уже есть дата, собирается из существующих таблиц; новая таблица — только для того, чего больше нигде нет (заметки, звонки, смена этапа). |
| 4 | Этапы и «Дальше» | Разделы 3.1 и 4.1. |
| 5 | Тендеры | Тот же каркас на карточке тендера (раздел 4). |

## 3. Страница частной заявки

### 3.1 Шапка: этапы и «Дальше»

```
ЧЗ-2026-0007 · ГБ № 2 Астаны                                       ⋯
✓ Обращение      ✓ Позиции     ● Цены           ○ КП        ○ Итог
  WhatsApp 12.10   3 шт          ответил 1 из 3
Дальше: ФОТЕК ответил, ждём ещё двоих; 1 письмо не ушло   [Таблица цен]
```

**Шаги:** Обращение → Позиции → Цены → КП → Итог. У заявки не из обращения первый шаг — «Создана ДД.ММ». Подпроект 3 вставит между КП и Итогом «Договор → Оплата → Поставка».

**Состояние шага:** сделано ✓, сейчас ●, впереди ○. Подпись под шагом:
- Обращение — канал и дата («WhatsApp 12.10», «Сайт 12.10», «Почта 12.10»);
- Позиции — «3 шт» / «нет позиций»;
- Цены — «ответил 1 из 3», «цены по 5 из 6»;
- КП — «№ 481 · черновик / отправлено 07.10 / принято / отклонено»;
- Итог — «купили у нас 12.10» / «не купили» / «отменена».

Клик по шагу прокручивает к его разделу.

**Какой шаг текущий** — по существующему этапу заявки (`PrivateRequestStageCalculator`): EMPTY → Позиции; NEW → Цены; REQUESTED → Цены; PRICED → КП; KP_DRAFT / KP_SENT / KP_REJECTED → КП; KP_ACCEPTED → Итог; WON / LOST / CANCELLED → все шаги сделаны, Итог показывает исход.

**«Главное» КП** для шага и подсказки (у заявки их может быть несколько): принятое → последнее отправленное → последний черновик. В ленте видны все.

**«Дальше»** — одна строка и кнопка, которая делает это действие:

| Где сделка | «Дальше» | Кнопка (код действия) |
|---|---|---|
| позиций нет | Добавьте позиции | — (прокрутка к позициям; `ADD_LINES`) |
| цены не запрашивали | Запросите цены у поставщиков | Запросить цены… (`REQUEST_PRICES`) |
| ждём ответов | Ответил 1 из 3; 1 письмо не ушло | Таблица цен (`OPEN_PRICES`) |
| цены есть | Цены есть по 5 из 6 позиций — можно делать КП | Создать КП клиенту (`CREATE_OFFER`) |
| КП — черновик | Доделайте и отправьте КП № 481 | Открыть КП (`OPEN_OFFER`) |
| КП отправлено | КП № 481 отправлено 07.10 — что ответил клиент? | Согласился / Отказался (`OFFER_DECISION`) |
| КП отклонено | Клиент отказался от КП № 481 — новое КП или закройте сделку | Создать КП клиенту (`CREATE_OFFER`) |
| КП принято | Клиент согласился — закройте сделку | Закрыть: купили у нас (`CLOSE_WON`) |
| закрыта | Закрыта: купили у нас, 12.10 | — («Вернуть в работу» — в меню ⋯) |

- «Ждём ответов»: ответил — запрос в статусе RESPONDED / DECLINED / ACCEPTED; «письмо не ушло» — `letter_status` NO_EMAIL / FAILED или возврат после последней отправки (как ячейка таблицы цен).
- «Согласился» / «Отказался» меняют статус главного КП (тот же путь, что в редакторе: ACCEPTED / REJECTED) и пишут событие (раздел 5).
- Кнопки «Дальше» видит только админ; оператор — этапы и текст.
- Шаги и «Дальше» считает сервер — одна логика на список заявок, шапку и подсказку.
- На телефоне шаги сжимаются в «Этап 3 из 5: Цены», под ними строка «Дальше».

### 3.2 Колонка «Переписка и история»

```
Переписка и история                                  свернуть ›
12.10 09:14  📥 Обращение (WhatsApp)
12.10 09:20  Клиент: «нужен АСД-ФОТЕК, комплект…»
12.10 09:31  Мы: «Добрый день, уточним цену…»
12.10 10:02  Создана заявка ЧЗ-2026-0007
13.10 11:40  ✉ Запрос цен → ФОТЕК, Аксион (письма), MEDSYST (передан вручную)
13.10 11:41  ⚠ Письмо Аксиону вернулось — адрес не существует
14.10 08:05  💡 ФОТЕК ответил: цены по 2 из 3, файл «КП 23142.xls» ›
15.10 16:20  📝 Заметка (vlad): «просит доставку в Каскелен»
16.10 12:00  📄 КП № 481 отправлено ›
16.10 18:30  ✓ Клиент согласился (vlad)
[+ Заметка] [+ Звонок]                  [Написать в WhatsApp ↗]
```

**Источники** (сервер собирает и упорядочивает по времени):
1. **Сообщения чата обращения** (WhatsApp или письма info@) — пузырями, общим компонентом `shared/chat-message`. Диапазон: от начала обращения (`lead.receivedAt`, как `ChatService.messagesForLead`) до начала следующего обращения в том же чате, если оно появилось; после создания заявки сообщения продолжают идти.
2. **События обращения** (`lead_event`): поступило, заметки, звонки, смена статуса.
3. **Создание заявки** — `tender.created_at` («Создана заявка ЧЗ-…»).
4. **Запросы цен** этой заявки: ушёл (`sent_at`; письмом / передан вручную — `letter_status` MANUAL), не ушёл (`letter_status` NO_EMAIL / FAILED), вернулся (строка «Входящих» BOUNCE, привязанная к запросу, после последней отправки), ответ поставщика (`response_date`: «цены по N из M» / «отказ»), файл ответа (`supplier_reply_file.created_at`). Запросы, отправленные в одну минуту (одно окно «Запросить цены»), — одной строкой.
5. **КП клиенту** этой заявки: создано (`created_at`), отправлено (`sent_at`).
6. **Новая таблица событий сделки** (раздел 5): заметки, звонки, смена этапа — с автором.

**Поведение:**
- Каждое событие — ссылка на своё место: ответ поставщика → экран сверки `/price-requests/{id}`, КП → редактор, сообщение → чат `/chats?chatId=`.
- Старые сверху, новые снизу; колонка открывается прокрученной вниз и держится у низа, пока пользователь не ушёл читать выше (как «Чаты», `ResizeObserver`, §14). Догрузка частями по 50 — «Показать раньше».
- Обновление: при возврате на вкладку и раз в 30 с, пока страница видна; после действий на странице (запрос цен, КП, статус, заметка) — сразу.
- «+ Заметка» и «+ Звонок» внизу — только админ (текст до 2000 символов).
- Отвечать клиенту из АИС нельзя (АИС — зеркало переписки): «Написать в WhatsApp ↗» (`wa.me`) или «Написать письмо ↗» (`mailto:`) — если у обращения есть чат с телефоном или адресом.
- Время — как на «Чатах».

### 3.3 Раскладка

- **Широкий экран (окно ≥ 1200 px):** две колонки. Слева — прежние разделы (клиент, позиции, поставщики и цены, КП клиенту), справа — колонка ленты (~380 px), липкая по высоте экрана, со своей прокруткой. «свернуть ›» убирает колонку, в шапке остаётся «Переписка ‹». Состояние помнит браузер (`localStorage['ais.deal.timeline']`, с try/catch, §12).
- **Узкий экран:** этапы и «Дальше» — сверху, под ними вкладки «Сделка | Переписка».
- Нижняя липкая кнопка телефона («Запросить цены» / «КП клиенту») уступает место строке «Дальше» — дублировать действие не нужно.

## 4. Карточка тендера

Тот же каркас: сверху этапы и «Дальше», справа колонка «История» (без переписки — у тендера нет чата с клиентом), на телефоне вкладки «Тендер | История».

### 4.1 Этапы и «Дальше»

```
17779323-1 · ГКП ГМБ № 2 Астаны · приём до 21.10 10:00              ⋯
✓ Лоты и ТЗ   ✓ Цены        ● Заявка      ○ Итог   ○ Договор   ○ Поставка   ○ Оплата
  5 лотов       по 5 из 5     № 386 черновик
Дальше: доделайте и подайте заявку — приём до 21.10 10:00   [Открыть заявку]
```

**Шаги:** Лоты и ТЗ → Цены → Заявка на участие → Итог → Договор → Поставка → Оплата.
- **Лоты и ТЗ:** у импортных тендеров — «ТЗ: N из M» по `tech_spec_status = OK`; у ручных — «N лотов», шаг сделан, если лоты есть.
- **Цены:** по `TenderWorkStageService` (NOT_STARTED / REQUESTED / PRICED / WINNER_SELECTED) — «ответил X из Y», «цены по N из M», «победители выбраны».
- **Заявка / Итог:** по заявке на участие тендера (`activity_apply`; если их несколько — последняя не отменённая): DRAFT — заявка текущая; SUBMITTED / UNDER_REVIEW — Итог текущий; WON / LOST / CANCELLED — исход. Отмена тендера на площадке (`tender.status = CANCELLED`) — исход «тендер отменён».
- **Договор / Поставка / Оплата** — из полей заявки на участие: `contract_number` / `contract_signed_at`, `delivery_status` (ORDERED / DELIVERED / PAID), `delivered_at`, `paid_at`. Здесь только показываются; правятся, как сейчас, на «Заявках на участие» (удобное ведение — подпроект 4).

| Где тендер | «Дальше» | Кнопка |
|---|---|---|
| у части лотов нет ТЗ (импорт) | Разберите ТЗ: 2 лота без ТЗ | к лотам |
| цены не запрашивали | Запросите цены по лотам | к лотам |
| ждём ответов | Ответил 1 из 3 | Запросы КП |
| цены есть | Сравните предложения и выберите победителей | Сравнить предложения |
| победители есть, заявки нет | Соберите заявку на участие | Сформировать заявку |
| заявка — черновик | Подайте заявку — приём до 21.10 10:00 | Открыть заявку |
| срок прошёл, заявки нет | Приём закрыт 21.10 — заявку не подали | — |
| подана / на рассмотрении | Ждём итога | — |
| выиграли | Заключите договор, затем поставка и оплата | Открыть заявку |
| оплачено | Сделка закрыта | — |

Срок — по правилу `ImportDeadline.passed` / `deadline_at` (время площадки, CLAUDE.md §8 «пакет 3»).

### 4.2 Колонка «История»
- Тендер найден (импорт с площадки, `tender.created_at`) или создан вручную.
- Запросы цен, письма, ответы поставщиков и их файлы — как в 3.2.
- Заявка на участие создана (`activity_apply.created_at`); договор, поставка и оплата — по датам из неё.
- Новая таблица: заметки и звонки (например, звонок заказчику), смена статуса заявки на участие, назначение победителя.
- Разбор ТЗ по лотам в историю не идёт (при 30 лотах — 30 одинаковых строк; состояние видно на шаге «Лоты и ТЗ»).

### 4.3 Раскладка
Как 3.3; карточка тендера — панель внутри `/tenders` (`tenders.component.ts`, ~1200 строк): каркас (этапы, «Дальше», колонка) выносится в общие компоненты; если обёртка карточки упирается в бюджет стилей компонента — карточку выделить в свой компонент.

## 5. Данные — таблица событий сделки (V32)

```sql
CREATE TABLE deal_event (
    id          BIGSERIAL PRIMARY KEY,
    tender_id   BIGINT       NOT NULL REFERENCES tender (id) ON DELETE CASCADE,
    type        VARCHAR(20)  NOT NULL,   -- NOTE / CALL / STAGE
    code        VARCHAR(40),             -- для STAGE: OFFER_STATUS, CLOSED, REOPENED, APPLY_STATUS, WINNER
    text        TEXT         NOT NULL,   -- текст строки ленты
    author      VARCHAR(100),            -- логин; пусто — система
    ref_id      BIGINT,                  -- КП / заявка на участие / лот, если есть
    occurred_at TIMESTAMPTZ  NOT NULL DEFAULT now()
);
CREATE INDEX idx_deal_event_tender ON deal_event (tender_id, occurred_at);
```

- Частная заявка и тендер — одна сущность `tender` (`source` PRIVATE_REQUEST / PUBLIC_TENDER), поэтому одна таблица на оба вида сделок.
- Не рыночная (без `@Filter`): читается только через тендер с гардом рынка (как `TenderLot`). Без CHECK на `type` / `code` — значения расширяются кодом (подпроекты 3 и 4), как `inbound_email.type`.
- Удаление заявки уносит события (`ON DELETE CASCADE`).

**Кто пишет:**
- `POST /api/private-requests/{id}/events` и `POST /api/tenders/{id}/events` `{type: NOTE | CALL, text}` — заметка и звонок (ADMIN).
- `ClientOfferService.setStatus` — у КП из заявки (`tender_id` задан) при смене статуса, кроме DRAFT → SENT (отправку и так показывает `sent_at`): «КП № N: клиент согласился / отказался», «КП № N: снова черновик».
- `PrivateRequestService.close` / `reopen` — «Закрыта: купили у нас / не купили / отменена», «Возвращена в работу».
- `ActivityApplyService.update` — смена статуса заявки на участие: «Заявка на участие № N: подана / на рассмотрении / выиграли / проиграли / отменена».
- `WinnerAssignmentService.assignWinner` — «Победитель по лоту «…»: <поставщик>, <цена>».
- Автор — логин текущего пользователя.

## 6. API

- `GET /api/private-requests/{id}` — в ответ добавляется `progress: {steps: [{key, state: DONE | CURRENT | TODO, label, detail}], next: {text, action, refId}}`.
- `GET /api/private-requests/{id}/timeline?before=<время>&limit=50` → `{items, hasMore}`; элемент: `{at, kind, text, author, link: {type, id}, message}` (`message` — `ChatMessageResponse` у сообщений чата). Виды: MESSAGE, LEAD_EVENT, CREATED, RFQ_SENT, LETTER_FAILED, BOUNCED, REPLY, REPLY_FILE, OFFER_CREATED, OFFER_SENT, NOTE, CALL, STAGE.
- `POST /api/private-requests/{id}/events` (ADMIN).
- Тендеры: `GET /api/tenders/{id}/progress`, `GET /api/tenders/{id}/timeline`, `POST /api/tenders/{id}/events` (ADMIN). Прогресс тендера — отдельным путём: `GET /api/tenders` отдаёт весь список, считать там прогресс каждого тендера незачем.
- Гарды: путь заявки — только `source = PRIVATE_REQUEST` текущего рынка (`PrivateRequestService.findById`); путь тендера — `PUBLIC_TENDER` текущего рынка; иначе 404. Оператор — 403 на запись.

**Сборка ленты** — один сервис (`DealTimelineService`): у каждого источника берётся до `limit` событий раньше `before` (по убыванию), всё сливается, отдаются `limit` самых поздних по возрастанию; `hasMore` — если хоть у одного источника осталось ещё.

## 7. Интерфейс

- `shared/deal-progress` — этапы и «Дальше» (вход: `progress`, `readonly`; выход: действие → обрабатывает страница: прокрутка, окно запроса цен, создание КП, смена статуса, закрытие).
- `shared/deal-timeline` — лента (вход: вид сделки и id, `readonly`): загрузка частями, сообщения через `shared/chat-message`, «+ Заметка / + Звонок», «Написать… ↗», прижатие к низу.
- Обе — общие для заявки и тендера; новое — в ленивых чанках (начальный бандл ≤ 1,5 МБ, §12).
- Стили — токены UI-kit, тинты по правилам §12, цели 40 px на телефоне, обе темы.

## 8. Крайние случаи

- **Заявка без обращения** (ручная, из письма «Входящих», из Excel): первый шаг — «Создана ДД.ММ», в ленте нет переписки и кнопки «Написать…».
- **Обращение без чата** (с сайта, телефон): события обращения есть, сообщений нет.
- **Обращение или чат удалены** — связь обнуляется (`ON DELETE SET NULL`), лента без переписки.
- **Несколько КП** — «главное» КП по правилу 3.1; в ленте — все.
- **Закрытая заявка** — «Дальше» показывает исход; «Вернуть в работу» — в меню ⋯.
- **Старые сделки** — всё, что собирается из существующих таблиц, появляется сразу; события новой таблицы — с момента запуска (когда раньше приняли или отклонили КП, неизвестно — такого события нет, статус виден в этапах).
- **Длинная переписка** — догрузка частями; лента не грузит всё сразу.

## 9. Проверка

- **Сервер** (тест красный до правки, мутация на каждое правило):
  - этапы и «Дальше» заявки — для каждого состояния 3.1 (в том числе «письмо не ушло», несколько КП, закрытая);
  - этапы и «Дальше» тендера — для каждой строки таблицы 4.1 (в том числе «срок прошёл, заявки нет», договор / поставка / оплата);
  - лента — каждый источник, порядок, граница переписки следующим обращением, группировка запросов цен одной минуты, догрузка (`before`, `hasMore`);
  - события — запись при смене статуса КП, закрытии и возврате заявки, смене статуса заявки на участие, назначении победителя; 403 оператору, 404 чужому рынку и чужому виду сделки, предел текста.
- **Фронт:** `npm run build`; живьём — настоящая сделка от обращения в WhatsApp до «купили у нас» (обращение → заявка → запрос цен → ответ → КП → «Согласился» → закрытие) и тендер (лоты → запрос цен → сравнение → победитель → заявка на участие → статус); 1280 / 390, обе темы, оператор (запросов записи 0).

## 10. Вне рамок

- Подпроекты 3 и 4 (после КП; хвост тендера).
- Ответ клиенту из АИС.
- Напоминания («КП без ответа 3 дня», «срок приёма завтра»).
- Лента на карточке обращения (обращение ссылается на заявку — этого достаточно).
- События смены этапа задним числом для старых сделок.
