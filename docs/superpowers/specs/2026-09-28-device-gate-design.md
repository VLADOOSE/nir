# Калитка по коду устройства для ais.westmed.kz — дизайн

**Дата:** 2026-09-28
**Статус:** утверждён оператором (части 1–3 согласованы в чате 2026-09-27/28)
**Контекст:** шаг 2 блока «доступ без Tailscale». Шаг 1 сделан 2026-09-27: `https://ais.westmed.kz` — nginx хоста, Let's Encrypt, общий пароль nginx (basic auth `westmed`), сильные пароли АИС (DEPLOY.md §6). CLAUDE.md §5 (прод; push делает оператор — авторежим не пускает агента деплоить), §6 (архитектура), §12 (UI-kit, мобильные карточки, тёмная тема).
**Запрос оператора:** «калитка по коду устройства» вместо общего пароля: посторонние не должны видеть даже страницу входа, а доступ выдаётся и отзывается по одному устройству.

## 1. Решения, принятые в обсуждении

| # | Вопрос | Решение |
|---|---|---|
| 1 | Как допускать новое устройство | **Код на устройстве, админ подтверждает в АИС.** Недопущенное устройство показывает код, админ находит запрос с этим кодом и жмёт «Допустить». Одноразовых кодов «от админа» нет |
| 2 | Как админ узнаёт о запросе | **Только в АИС:** счётчик в меню и раздел «Устройства». Код сотрудник сообщает сам (звонок, WhatsApp). Telegram — позже, отдельным шагом |
| 3 | Где проверять | **nginx хоста** (`auth_request`) на каждый запрос спрашивает АИС; недопущенным отдаётся только калитка. Модуль на сервере есть — `nginx -V`: `--with-http_auth_request_module` |
| 4 | Срок жизни допуска | До отзыва; устройство, не заходившее **90 дней**, выпадает само |
| 5 | Кто допускает | Только роль ADMIN |
| 6 | Запасной вход | Tailscale и SSH-туннель ходят на `127.0.0.1:8090` мимо nginx хоста — калитки там нет, намеренно |
| 7 | Общий пароль nginx | На переходе остаётся **только на калитке и её API**: посторонний, чтобы хотя бы попросить доступ, должен знать пароль. После проверки снимается |
| 8 | Отвергнуто | Проверка только в АИС — посторонние видят форму входа и код приложения. Клиентские сертификаты — установка на телефоны сотрудников слишком мучительна |

## 2. Как это работает для людей

**Калитка** — что видит недопущенное устройство на `ais.westmed.kz`:
1. Нейтральный заголовок «Служебный вход» — без названия системы и компании. Поле «Как вас зовут» и кнопка «Запросить доступ».
2. После нажатия — крупный код `7K4-QM2` и «Сообщите код администратору. Страница откроется сама, когда доступ подтвердят». Страница сама проверяет статус раз в 3 секунды.
3. Допустили — страница сама переходит ко входу в АИС. Отклонили — «Запрос отклонён» и кнопка «Запросить снова». Через 15 минут без решения — «Запрос истёк» и та же кнопка.

**Раздел «Устройства»** (Система → Устройства, только ADMIN): счётчик ожидающих запросов в меню; **запросы** — код крупно, имя, устройство («iPhone · Safari»), IP, когда, поле подписи (по умолчанию имя из запроса), «Допустить» / «Отклонить»; **допущенные** — подпись, устройство, кто и когда допустил, последний визит, «Отозвать»; **история** — отклонённые, отозванные, истёкшие (свёрнута).

**Правила:**
- Допущенное устройство работает до отзыва; 90 дней без визитов — выпадает само.
- Отзыв действует сразу, даже на открытую вкладку: следующий же запрос уводит на калитку.
- Калитка не заменяет вход в АИС: после неё — обычный логин и пароль.
- «Устройство» — это браузер: другой браузер, инкогнито, очистка данных браузера, иконка АИС на экране iPhone (у неё своя память) — каждый раз отдельное устройство.
- Защита от спама: с одного IP — не больше 3 запросов в минуту (запас 2); ожидающих запросов одновременно — не больше 20.

## 3. Архитектура

```
браузер ──▶ nginx хоста: ais.westmed.kz (TLS)
              │  auth_request /__gate_check ──▶ 127.0.0.1:8090 ──▶ АИС GET /api/gate/check
              │                                                     реестр в памяти → 204 | 401
              ├─ 204 → proxy_pass 127.0.0.1:8090 — как сейчас (фронт-контейнер, /api → бэкенд)
              └─ 401 → @gate: страница → 302 /gate/;  /api/… → 401 + заголовок X-AIS-Gate: device

Tailscale / SSH-туннель ──▶ 127.0.0.1:8090 напрямую — калитки нет (запасной вход админа)
```

Проверка **закрыта по умолчанию**: если АИС не ответила на подзапрос (упала, таймаут), nginx не пропускает никого.

## 4. Данные — миграция `V19__trusted_device.sql`

```sql
CREATE TABLE trusted_device (
    id              BIGSERIAL PRIMARY KEY,
    token_hash      VARCHAR(64)  NOT NULL UNIQUE,   -- SHA-256 (hex) ключа устройства; сам ключ не хранится
    status          VARCHAR(10)  NOT NULL,          -- PENDING / TRUSTED / REJECTED / REVOKED / EXPIRED
    code            VARCHAR(6)   NOT NULL,          -- код запроса без дефиса (показ — «7K4-QM2»)
    requester_name  VARCHAR(60)  NOT NULL,          -- что ввели на калитке; НЕ доверенное
    label           VARCHAR(100),                   -- подпись админа при допуске
    user_agent      VARCHAR(300),
    ip              VARCHAR(45),
    requested_at    TIMESTAMPTZ  NOT NULL DEFAULT now(),
    decided_at      TIMESTAMPTZ,
    decided_by      VARCHAR(100),                   -- логин админа
    last_seen_at    TIMESTAMPTZ
);
CREATE INDEX idx_trusted_device_status ON trusted_device (status);
-- код уникален среди ожидающих: по нему админ находит нужный запрос
CREATE UNIQUE INDEX uq_trusted_device_pending_code ON trusted_device (code) WHERE status = 'PENDING';
```

Таблица **общая, без рынка** — как `user_account`: доступ к системе не зависит от переключателя РФ/KZ (без `@Filter`, без `MarketStampingListener`).

## 5. Статусы

| Из | Событие | В |
|---|---|---|
| — | «Запросить доступ» | PENDING |
| PENDING | «Допустить» | TRUSTED |
| PENDING | «Отклонить» | REJECTED |
| PENDING | 15 минут без решения | EXPIRED |
| TRUSTED | «Отозвать» | REVOKED |
| TRUSTED | 90 дней без визитов (считая от `max(last_seen_at, decided_at)`) | EXPIRED |

REJECTED, REVOKED и EXPIRED — конечные. Новый запрос с того же браузера — новая строка с **новым** ключом; старая остаётся в истории.

## 6. Ключ устройства и код

- **Ключ:** 32 байта из `SecureRandom` → base64url (43 символа). Cookie `ais_device`: `Path=/; HttpOnly; Secure; SameSite=Lax; Max-Age=34560000` (400 дней — предел Chrome). JavaScript страницы ключа не видит; в БД — только SHA-256.
- **Код:** 6 символов из алфавита `23456789ABCDEFGHJKMNPQRSTUVWXYZ` (31 символ, без 0/O/1/I/L — не путаются на слух и на экране), около 887 млн вариантов; показ — `XXX-XXX`. При совпадении с ожидающим запросом — сгенерировать заново.
- **Код — метка, а не секрет.** Знание кода ничего не даёт: допуск делает только админ, и только по коду, названному ему знакомым человеком. Имя в запросе посторонний может написать любое — поэтому в интерфейсе решает код, а имя — справочно.

## 7. REST API

**Калитка — `/api/gate`** (`permitAll`, ответы с `Cache-Control: no-store`):

| Метод | Путь | Ответ |
|---|---|---|
| GET | `/check` | 204 — ключ из cookie принадлежит допущенному устройству; иначе 401. Без тела, без обращения к БД. Снаружи закрыт на nginx (только внутренний подзапрос) |
| POST | `/request` `{name}` | 200 `{state:"PENDING", code, expiresAt}` + `Set-Cookie` с новым ключом. Если cookie уже принадлежит ожидающему запросу — тот же код, без новой строки; если допущенному — `{state:"TRUSTED"}`. Имя 1–60 символов после обрезки пробелов, иначе 400. Уже 20 ожидающих — 429 |
| GET | `/status` | `{state: NONE \| PENDING \| TRUSTED \| REJECTED \| REVOKED \| EXPIRED, code?, expiresAt?}` по cookie |

**Администрирование — `/api/devices`** (`@PreAuthorize("hasRole('ADMIN')")`):

| Метод | Путь | Ответ |
|---|---|---|
| GET | `/` | `{pending:[…], trusted:[…], history:[… последние 50]}`; элемент — `{id, status, code, requesterName, label, device, ip, requestedAt, decidedAt, decidedBy, lastSeenAt, current}` |
| GET | `/pending-count` | `{count}` — для счётчика в меню |
| POST | `/{id}/approve` `{label?}` | только из PENDING, иначе 409; подпись по умолчанию — имя из запроса |
| POST | `/{id}/reject` | только из PENDING, иначе 409 |
| POST | `/{id}/revoke` | только из TRUSTED, иначе 409 |

- `current: true` — у устройства, чей ключ пришёл в cookie этого же запроса (админ видит «это устройство»). Через туннель и Tailscale cookie калитки нет — пометки тоже.
- `device` — `UserAgentSummary` из `user_agent`: «iPhone · Safari», «Android · Chrome», «Mac · Chrome», «Windows · Edge» и т. п.; нераспознанное — «Браузер».
- IP — **предпоследний** адрес `X-Forwarded-For`: nginx хоста *дописывает* реальный адрес клиента к тому, что клиент прислал сам (первый адрес подделывается), а фронт-контейнер дописывает свой шаг последним. Адрес один — берётся он; заголовка нет — адрес соединения. IP справочный: чтобы узнать устройство, а не чтобы что-то решать.
- Реестр в памяти обновляется **после коммита**: изменения БД делает отдельный бин `TrustedDeviceWriter` (своя транзакция на метод, приём проекта, CLAUDE.md §6), и сервис трогает реестр только после возврата из него. Допуск и отзыв действуют со следующего же запроса, провалившийся коммит реестр не меняет. Колбэк `TransactionSynchronization.afterCommit` не годится: `@Transactional`-тесты не коммитят — тесты не увидели бы допуска.

## 8. Реестр в памяти и фоновые задачи

- `DeviceRegistry` — `ConcurrentHashMap<хеш, запись>` допущенных устройств. Заполняется из БД при старте (`ApplicationReadyEvent`) — перезапуск и деплой допуски не сбрасывают; пополняется при допуске, чистится при отзыве и истечении.
- `/api/gate/check` смотрит только в реестр и помечает визит **в памяти** — БД на каждый запрос не трогается.
- `DeviceGateScheduler` — одна задача раз в 5 минут, по порядку: накопленные отметки визитов одной пачкой в `last_seen_at` → ожидающие старше 15 минут → EXPIRED → допущенные без визитов 90 дней → EXPIRED (и вон из реестра). Визиты пишутся **первыми**: иначе устройство, заходившее минуту назад, выпало бы по старой отметке в БД. Чаще не нужно: свежесть запроса проверяется на лету при каждом чтении (статус, счётчик, список, лимит), а задача лишь фиксирует её в БД. Задача короткая — общий пул `@Scheduled` подходит (в отличие от очереди разбора ТЗ, CLAUDE.md §8).
- Бэкенд один — реестр в памяти и есть источник правды для проверки; БД — для хранения и истории.

## 9. nginx хоста — `deploy/nginx/zz-ais.westmed.kz.conf`

Итоговое состояние сервера 443 (блок 80, SSL и заголовки безопасности — без изменений):

```nginx
limit_req_zone $binary_remote_addr zone=ais_gate:1m rate=3r/m;      # новая зона — запросы доступа

    # (было: auth_basic "AIS"; auth_basic_user_file /etc/nginx/.htpasswd-ais;)
    # калитка: по умолчанию каждая локация сперва спрашивает АИС, допущено ли устройство
    auth_request /__gate_check;

    location = /__gate_check {
        internal;
        auth_request off;
        proxy_pass http://127.0.0.1:8090/api/gate/check;
        proxy_pass_request_body off;
        proxy_set_header Content-Length "";
        proxy_set_header Host $host;
        proxy_connect_timeout 3s;
        proxy_read_timeout 5s;
    }

    # недопущенное устройство: страница → на калитку; API → 401 с пометкой
    location @gate {
        if ($uri ~ ^/api/) {
            add_header X-AIS-Gate "device" always;
            return 401;
        }
        return 302 /gate/;
    }

    location /gate/ {                  # калитка
        auth_request off;
        expires -1;
        proxy_pass http://127.0.0.1:8090;
    }
    location = /api/gate/status {      # калитка
        auth_request off;
        proxy_pass http://127.0.0.1:8090;
    }
    location = /api/gate/request {     # калитка
        auth_request off;
        limit_req zone=ais_gate burst=2 nodelay;
        proxy_pass http://127.0.0.1:8090;
    }
    location = /api/gate/check { auth_request off; return 404; }   # снаружи не нужен
    location = /robots.txt     { auth_request off; …как сейчас… }

    location = /api/auth/login { error_page 401 = @gate; …как сейчас… }
    location /                 { error_page 401 = @gate; …как сейчас… }
```

(в каждой `proxy_pass`-локации — те же `proxy_set_header` и `proxy_cookie_path`, что сейчас.)

- `error_page 401 = @gate` стоит **только в проксирующих локациях под калиткой** и ловит лишь 401, **сгенерированный самим nginx** (`auth_request`). Собственный 401 АИС («сессия истекла») проходит к приложению как есть — `proxy_intercept_errors` выключен.
- `/__gate_check` сам проверке не подлежит — `auth_request off`, иначе подзапрос проверки спрашивал бы сам себя.
- В `/gate/` — `expires -1`, а не `add_header`: собственный `add_header` в локации отключил бы унаследованные серверные заголовки (HSTS, `X-Robots-Tag`…).
- **Переходное состояние** (шаг 3 раскатки) получается из итогового одной командой — в три локации с пометкой `# калитка` дописывается пароль:
  `perl -pe 's{(# калитка)$}{$1\n        auth_basic "AIS"; auth_basic_user_file /etc/nginx/.htpasswd-ais;}'` (perl, а не `sed … a\`: однострочная форма `a\` в BSD sed на Mac не работает).
  Своего `error_page` в этих локациях нет, поэтому 401 от basic auth уходит браузеру как есть — с окном пароля, а не редиректом на калитку. Источник правды один — файл в репо.
- **Всё это проверяется на репетиции** (§14) на nginx 1.18 — той же версии, что на сервере: связка `auth_request` + `error_page` + именованная локация + `if` + наследование `add_header` — место, где nginx легко понять неправильно.

## 10. Калитка — `frontend/public/gate/index.html`

- Самостоятельная страница: HTML + CSS + JS в одном файле, без Angular и без внешних ресурсов (шрифты, иконки — встроенные). Иконка вкладки — тоже встроенная (`<link rel="icon" href="data:,">` или data-URI SVG): иначе браузер сам попросит `/favicon.ico`, а этот запрос идёт через проверку устройства и получит редирект. Попадает в сборку как статический файл (`public/` → корень `dist`) и уезжает на прод обычным деплоем фронта; фронт-контейнер отдаёт её по `/gate/` (`try_files $uri $uri/`).
- Мобильная вёрстка первым делом; светлая и тёмная тема — `prefers-color-scheme`, а если в `localStorage['ais.theme']` выбрана тема — она (тот же origin).
- Состояния: форма (имя + кнопка) → ожидание (код + «страница откроется сама») → переход на `/` (`location.replace`) | «Запрос отклонён» | «Запрос истёк» | «Слишком много запросов, попробуйте через несколько минут» (429) | «Нет связи — повторяю…» (сеть).
- При загрузке — `GET /api/gate/status`: если уже допущено — сразу `location.replace('/')`; если есть ожидающий запрос — сразу экран с его кодом (перезагрузка страницы не теряет код).

## 11. Раздел «Устройства» (Angular)

- Маршрут `/devices`, пункт «Устройства» в группе «Система» (только ADMIN) со счётчиком ожидающих — как счётчик «Обращений» (`.nav-count`, опрос раз в 60 с и при навигации).
- Страница: **Запросы** — карточки, код крупно, имя, устройство, IP, «2 мин назад», поле подписи, «Допустить» / «Отклонить»; пока страница открыта, список обновляется раз в 5 с (админ видит, как запрос появляется). **Допущенные** — подпись, устройство, кто и когда допустил, последний визит, пометка «это устройство», «Отозвать» с подтверждением; для «это устройство» подтверждение называет последствие («вы потеряете доступ с этого браузера, вернуться — через Tailscale/туннель»). **История** — свёрнута, последние 50.
- UI-kit проекта (CLAUDE.md §12): токены, светлая и тёмная тема, карточки `card-grid` ≤900px, тач-таргеты, `@media` в конце стилей.
- `authInterceptor`: 401 с заголовком `X-AIS-Gate: device` → `window.location.assign('/gate/')` — полная навигация, без вызова logout (он тоже упёрся бы в калитку). Прочие 401 — как сейчас (logout + `/login`).

## 12. Безопасность и крайние случаи

- **Закрыто по умолчанию.** Нет ответа от АИС — nginx не пускает (500/502). Калитка никогда не открывается «сама».
- **Ключ не подобрать и не прочитать скриптом:** 256 бит, `HttpOnly`; в БД — хеш, утечка базы не даёт выдать себя за устройство.
- **Подбор пароля АИС снаружи невозможен:** до формы входа доходят только допущенные устройства.
- **Отозвать своё устройство случайно нельзя:** пометка «это устройство» + подтверждение с последствием. Все устройства потеряны — вход через Tailscale или SSH-туннель.
- **Спам запросами:** 3 в минуту с IP (nginx) + не больше 20 ожидающих (АИС, 429) + истечение через 15 минут; имя ≤ 60 символов, `User-Agent` обрезается до 300.
- **Кеш:** ответы `/api/gate/*` — `no-store`; страница калитки — `expires -1`.
- **Отклонённый запрос** можно повторить — с теми же лимитами.
- **Cookie за двумя прокси:** хостовый `proxy_cookie_path` допишет `Secure; SameSite=Lax` и к `ais_device`, у которого эти атрибуты уже есть, — дубль атрибутов браузеры принимают, вреда нет.

## 13. Раскатка — без риска запереть самих себя

1. **Код.** Мерж → оператор делает push (`! git push origin main`, CLAUDE.md §5) → деплой. nginx не трогаем: работает общий пароль, код калитки лежит без дела (проверку никто не зовёт).
2. **Запасная консоль.** Вкладка с АИС через SSH-туннель (`http://localhost:8090`) — отсюда допускаются устройства; калитки на туннеле нет.
3. **Калитка + пароль на калитке** (переходное состояние §9). Оператор открывает `ais.westmed.kz` с Mac и с телефона → пароль → калитка → запрос → допуск из запасной вкладки → вход в АИС. Проверяем весь путь, включая отзыв и уход открытой вкладки на калитку.
4. **Снимаем пароль** в трёх локациях калитки и удаляем `/etc/nginx/.htpasswd-ais`; `ais-gate.pass` у оператора больше не нужен.
5. **Откат** на любом шаге — прежний конфиг: установка идёт тем же скриптом, что в шаге 1 (при провале `nginx -t` сам возвращает прежний файл), эталоны лежат в репо.

## 14. Тестирование

- **Бэкенд** (`@SpringBootTest @Transactional` на nirdb, как принято):
  - `DeviceTokens`: длина и алфавит ключа и кода, хеш детерминирован;
  - запрос доступа ставит cookie и выдаёт код; повтор с тем же cookie — тот же код и без новой строки; с cookie допущенного — `TRUSTED`;
  - `/check`: 204 для допущенного; 401 для ожидающего, отклонённого, отозванного, истёкшего, неизвестного, пустого и битого cookie;
  - допуск, отклонение, отзыв: действуют сразу (следующий `/check`), недопустимые переходы — 409, оператор получает 403;
  - лимит: 21-й ожидающий запрос — 429; имя пустое/длиннее 60 — 400;
  - истечения: ожидающий старше 15 минут и допущенный без визитов 90 дней → EXPIRED и вон из реестра; сброс визитов в `last_seen_at`;
  - реестр после «перезапуска» (новый экземпляр) восстанавливается из БД;
  - `UserAgentSummary` — golden-набор строк реальных браузеров;
  - ключевые гарды — прогон **мутациями** (CLAUDE.md §14): ломаю условие — краснеет ровно свой тест.
- **Фронт:** `npm run build`; калитка и раздел — вживую в Playwright на 1280 и 390, светлая и тёмная тема.
- **Репетиция nginx:** локально в Docker `nginx:1.18` с конфигом §9 (итоговым и переходным) перед локальной АИС: без cookie страница → 302 `/gate/`, `/api/…` → 401 с `X-AIS-Gate`; собственный 401 АИС проходит как есть; допущенный cookie → 200; переходный пароль на калитке показывает окно пароля, а не редирект; `/api/gate/check` снаружи → 404.
- **Прод:** шаги 3–4 §13 — Mac и телефон; `curl` снаружи (без cookie → 302/401; соседи westmed.kz и vital-spb.kz → 200; голый IP — как до изменений).
