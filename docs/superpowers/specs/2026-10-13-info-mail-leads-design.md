# Письма клиентов на info@westmed.kz → «Обращения»

**Дата:** 2026-10-13. **Статус:** дизайн согласован с оператором в чате 2026-10-13 (вариант «полностью, обращениями»; подход «почта — канал чатов»).
**Связано:** приём почты zakup@ (спека `2026-10-05-zakup-mail-telegram-design.md`, CLAUDE.md §8 «Почта zakup@ → Telegram», §9), обращения (`2026-09-27-leads-westmed-intake-design.md`), чаты WhatsApp (`2026-09-28-whatsapp-chats-green-api-design.md`, дельта `2026-09-28-whatsapp-waha-design.md`).

## 1. Зачем

Клиент может написать West-Med не только через сайт, звонком или в WhatsApp, но и письмом на info@westmed.kz. Сейчас эти письма в АИС не попадают. Их видят только в почте и в теме 30 группы «Заявки»: туда их шлёт сторонний проект medsite через роботный ящик на Яндексе. Обращением письмо не становится, в работу его берут по памяти.

**Цель:** письмо клиента на info@ становится обращением в «Обращениях» — рядом с заявками сайта и звонками. Дальше та же цепочка: «Взять в работу» → «Создать заявку» → запрос цен → КП клиенту. Переписка — письма клиента и наши ответы — видна в карточке обращения.

**Что лежит в ящике** (разведка 2026-10-13, только чтение): за 5,5 месяца 75 писем.

| Вид | Писем |
|---|---|
| Предложения зарубежных производителей | 23 |
| Уведомления сайта о заявках (они уже приходят обращениями через API сайта) | 19 |
| Рассылки | 13 |
| Служебные (Mail.ru, 2ГИС, СК-Фармация, госзакуп) | 12 |
| Личные почты и компании KZ/RU — похоже на клиентов | 7 |
| Свой домен | 1 |

Вложений с Excel не было ни разу. Пересылка в робот хранит копию в info@. Писем мало, поэтому правила простые, а редкий промах закрывается одной кнопкой «Не клиент».

## 2. Что входит

### 2.1 Второй ящик

- Отдельная настройка `mail.clients.*` (`MAIL_CLIENTS_*`): адрес, пароль, рынок (KZ), частота опроса, окно первого запуска, предел файла, служебные домены. По умолчанию выключена. Приём zakup@ (`mail.imap.*`) не меняется: его поток, курсор, ответы поставщиков и Telegram — как были.
- Свой однопоточный поток. Рынок ящика ставится в потоке явно (CLAUDE.md §6).
- **Только чтение, как у zakup@:** EXAMINE и `BODY.PEEK` — письма у людей остаются непрочитанными.
- **Две папки:**
  - «Входящие»;
  - «Отправленные» — ищется по признаку `\Sent` (у Mail.ru он есть), а без признака — по имени «Отправленные» / «Sent».
- **Курсор по UID — у каждой папки свой:** ящик + папка. Письмо, пришедшее во время простоя, не теряется.
- **Первый запуск** (курсора нет или сменился `UIDVALIDITY`) — окно 7 дней, настраивается. Полугодовую историю не тянем.
- **Повторы:** одно и то же письмо — одно сообщение переписки. Ключ — Message-ID; у письма без него — номер письма в папке.
- **Сбои — как у zakup@:**
  - письмо, которое не разобралось или не записалось не по вине базы, — короткая строка во «Входящих» с причиной, курсор идёт дальше;
  - обрыв связи или недоступная база — проход останавливается, курсор остаётся на последнем записанном, повтор следующим проходом.

### 2.2 Куда идёт письмо из «Входящих»

Порядок правил значим:

1. **Уведомление сайта о заявке** (от info@westmed.kz, тема «… — westmed.kz») — пропуск, курсор дальше. Заявка уже пришла обращением через API сайта.
2. **Возврат, задержка доставки, автоответ, квитанция о прочтении** — во «Входящие», без обращения (правила `MailClassifier`).
3. **Рассылка** (заголовки `List-Unsubscribe` / `List-Id` или `Precedence: bulk|list|junk`) — во «Входящие».
4. **Служебное:**
   - служебное имя адреса: `noreply`, `no-reply`, `not-reply`, `donotreply`, `do-not-reply`, `mailer-daemon`, `postmaster`;
   - или домен из списка служебных: по умолчанию поддомены `mail.ru` (но не сам `mail.ru` — это личные ящики), `2gis.ru`, `2gis.com`, `ecc.kz`, `goszakup.gov.kz` со всеми поддоменами; список настраивается.

   Такие письма — во «Входящие».
5. **Свой домен** (`westmed.kz`) — во «Входящие».
6. **Всё остальное** — в переписку с адресом отправителя (§2.3).

«Входящие» — общий журнал почты обоих ящиков: у строки есть ящик, у экрана — фильтр по нему (§3).

### 2.3 Переписка

- **Переписка — одна на адрес собеседника в ящике info@.** Это чат с каналом «Почта»: `channel = EMAIL`, `account` — адрес ящика, `external_chat_id` — адрес собеседника в нижнем регистре. Название — имя отправителя из письма, иначе адрес. Телефона нет.
- **Сообщение — это письмо**, вид `EMAIL`:
  - тема (новое поле сообщения);
  - текст — HTML переводится в текст, процитированные прежние письма отрезаются: вся цепочка и так видна в ленте;
  - направление: входящее — письмо собеседника, исходящее — наше из «Отправленных»;
  - время;
  - вложения.
- **Вложения** — все, кроме встроенных картинок подписи. Предел — 25 МБ на файл, настраивается. Файл больше предела показывается названием с пометкой «не сохранён — откройте в почте». Отдаются так же, как вложения WhatsApp: только через переписку своего рынка, в браузере открываются только картинки, остальное скачивается.
- **Наше письмо из «Отправленных»** попадает в переписку с каждым адресатом из «Кому» и «Копия». Исключения — адреса нашего домена `westmed.kz` и служебные адреса по правилу §2.2 п. 4: в «Отправленных» больше всего ответов в поддержку Mail.ru и 2ГИС, и заводить на них переписки незачем. Если переписки с адресатом нет, она заводится без обращения — написали первыми мы.

### 2.4 Обращения

Правила — те же, что у чатов WhatsApp (`ChatLeadRules`, `ChatIngestWriter`):

- **Входящее письмо без открытого обращения заводит новое** — через единую точку входа `LeadIntakeService.ingest`:
  - статус «Новое», канал «Почта»;
  - тема — тема письма (пустая — «Письмо»);
  - контакт — имя и адрес отправителя; текст — текст письма без цитаты, не длиннее 4 000 символов;
  - клиент — среди «Учреждений» по адресу почты, если совпадение однозначное (`LeadClientMatcher`);
  - источник — `email`, внешний ключ — по письму.
- **Открытое обращение** ищется по переписке, иначе по адресу почты обращения без учёта регистра. Так письмо склеивается с заявкой с сайта от того же адреса. «Новое» и «В работе» — открытые всегда, «Превращено в заявку» — ещё 30 дней.
- **Следующие письма** ложатся в ту же переписку и в открытое обращение. Нового обращения нет.
- **Наше письмо из почты** (из «Отправленных») переводит «Новое» → «В работе». У обращения с сайта меняется и статус на сайте — как ответ с телефона в WhatsApp.
- **«Не клиент»:** в переписке с такой отметкой письма ложатся, но обращений не заводят.

### 2.5 «Не клиент»

- Кнопка «Не клиент» в карточке обращения из почты (только администратор). Она:
  - закрывает обращение с новой причиной «Не клиент»;
  - ставит отметку «не клиент» его почтовой переписке.
- Снять отметку можно на «Чатах» — переключатель уже есть. Закрытое обращение не открывается само; при необходимости — «Вернуть в работу», как сейчас.
- Предложения поставщиков, служебные адреса, не пойманные правилами §2.2, и прочий шум закрываются так один раз на адрес.

### 2.6 Позиции из Excel

У Excel во вложении письма — «Разобрать в позиции»: та же сетка разбора и тот же путь, что у Excel из WhatsApp (`POST /api/leads/{id}/items/import`). Дальше «Создать заявку».

## 3. Экраны

- **Карточка обращения:**
  - письма в общей ленте «Лента и переписка», вперемешку с событиями по времени: тема, текст (длинный свёрнут — «Показать полностью»), вложения;
  - «Открыть всю переписку» — на «Чаты»;
  - у контакта — адрес почты ссылкой `mailto:`;
  - кнопка «Не клиент» — у обращения из почты, только администратор.
- **«Чаты»:**
  - почтовые переписки в общем списке с меткой «Почта», новый фильтр «Почта»;
  - письмо в переписке — тема, текст, вложения; наши письма — справа, как ответы с телефона;
  - в шапке переписки — адрес вместо телефона;
  - строка состояния WhatsApp и подсказка про рынок у почтовой переписки не показываются;
  - поиск по названию, адресу и тексту.
- **«Входящие»:** колонка «Ящик» и фильтр «Все / zakup@ / info@».
- **«Обращения»:** канал «Почта» в списке и фильтре уже есть.
- **Телефон** (≤ 900 px): те же правила раскладки, что у чатов WhatsApp и «Входящих»; цели 40 px.

## 4. Что не меняется

- **Telegram:** письма info@ по-прежнему шлёт в тему 30 medsite (решение оператора). АИС об info@ уведомлений не шлёт. medsite и пересылку в робот не трогаем.
- **zakup@:** приём, ответы поставщиков, «Проверить почту» / «Проверить ответы», Telegram — как были.
- **Ответы клиенту пишут в почте:** отправки писем из АИС нет.
- **info@vital-spb.kz** — не трогаем.

## 5. Модель данных и API

- **Миграция V29:**
  - `chat_message.subject` (TEXT, у сообщений WhatsApp пусто);
  - курсор почты — на ящик + папку: колонка `folder` в `mail_cursor`; прежняя строка zakup@ становится папкой «Входящие».
- **Без миграции** (колонки — строки без ограничений):
  - вид сообщения `EMAIL`;
  - причина закрытия `NOT_CLIENT`;
  - канал чата `EMAIL` — значение `LeadChannel` уже есть.
- **API:**

  | Метод и путь | Права | Что делает |
  |---|---|---|
  | `GET /api/chats?filter=EMAIL` | вошедший | Новое значение фильтра — почтовые переписки |
  | `GET /api/chats/{id}/messages` | вошедший | У сообщения — `subject` |
  | `POST /api/leads/{id}/not-client` | ADMIN | Закрыть с причиной «Не клиент» и отметить почтовую переписку обращения; у обращения без почтовой переписки — 400 |
  | `GET /api/inbound?mailbox=` | вошедший | Фильтр по ящику; без параметра — оба |

## 6. Раскатка

- Деплой несёт миграцию V29 и выключенный приём.
- Пароль приложения info@ лежит у оператора в `~/.config/ais/info.pass`. Его прислали в чат, поэтому перед включением на проде пароль лучше перевыпустить: Mail.ru → Безопасность → «Пароли для внешних приложений».
- На сервер пароль кладёт скрипт `deploy/set-info-mail.sh`, запускает оператор командой `!`. Скрипт:
  - делает копию `.env`;
  - дописывает `MAIL_CLIENTS_*`;
  - проверяет вход по IMAP;
  - пересоздаёт бэкенд.
- Порядок — новый раздел DEPLOY.md.
- **Приёмка на проде:**
  1. письмо с личной почты на info@ → «Новое» обращение за минуту;
  2. ответ из веб-почты info@ → «В работе»;
  3. тестовое обращение закрыть.

## 7. Проверка

- **Тесты на GreenMail** (ящик info@ с «Входящими» и «Отправленными»):
  - правила §2.2 — каждое;
  - новое обращение; продолжение в открытом; склейка с обращением сайта по адресу;
  - «Превращено» — 30 дней;
  - «В работе» по нашему письму; «написали первыми» — без обращения;
  - «Не клиент»: кнопка и последующие письма;
  - повторы по Message-ID и без него;
  - предел вложений, встроенные картинки;
  - курсоры двух папок, окно первого запуска, новый `UIDVALIDITY`;
  - письма не становятся прочитанными;
  - zakup@ работает как раньше — прежние почтовые тесты зелёные;
  - гард рынка у вложений и у «Не клиент»; права (оператор — 403).
- **Каждое правило — мутацией** (CLAUDE.md §14).
- **Живьём локально** (GreenMail `./gradlew devMail` с ящиком info@ и скрипт писем):
  - письмо клиента с Excel → обращение → «Разобрать в позиции» → «Создать заявку»;
  - наш ответ → «В работе»;
  - рассылка и служебное — во «Входящих»; уведомление сайта — пропуск;
  - «Не клиент»;
  - 1280 и 390, обе темы, оператор.

## 8. Вне объёма

- Отправка писем из АИС, шаблоны ответов.
- Уведомления АИС в Telegram о письмах info@ (их шлёт medsite).
- Импорт истории старше окна первого запуска.
- Папка «Спам» (её разбирает фильтр Mail.ru) и письма, которые правила почты уносят из «Входящих».
- Слияние переписок одного клиента с разных адресов.
- info@vital-spb.kz.

## 9. Известные ограничения

- Служебные адреса, не пойманные правилами §2.2 (например, `support@` сервисов вне списка доменов), заведут обращение. Его закрывают «Не клиент» один раз на адрес.
- Клиент, пишущий с двух адресов, — две переписки и, возможно, два обращения. Второе закрывают причиной «Дубль».
- Письмо, которое правила Mail.ru унесли из «Входящих», не видно.
- Письмо клиента через сторонний сервис форм приходит со служебного адреса, а клиент — в Reply-To. Такое письмо уйдёт во «Входящие» по правилу §2.2 п. 4, а не в обращение.
