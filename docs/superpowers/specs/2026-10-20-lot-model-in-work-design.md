# «Модель в работе» лота — закрепить модель после ответа ИИ

**Дата:** 2026-10-20. **Рынок:** KZ (тендеры). **Объём:** полный, ≈ день (выбор оператора).
**Связано:** спека `2026-10-20-product-spec-fit-design.md` (сверка ТЗ с нашими товарами, «📋 Для ИИ»).

## 1. Зачем

Оператор (2026-10-20): «идеала не добьёмся, фича с копированием для ИИ будет в помощь — можно будет закинуть, а потом уже
точно выбрать то, что ИИ выдал, и закрепить конкретную модель под лот».

Сверка ТЗ без LLM честно говорит «◐ похоже» и «нет данных» там, где характеристик мало; «📋 Для ИИ» отдаёт тендер
Claude / Gemini, и ИИ советует модель — нашу с сайта или любую зарегистрированную в РК. Сейчас закрепить совет нечем:
«Предложено: …» у лота (`tender_lot.proposed_equipment_id` → `med_equipment`) ставится только из кандидатов реестра
(«Подбор» → «Взять в работу»), комплектности и подбора по каталогу; наш товар сайта закрепить нельзя, «ещё: …» в сверке
только переключает показ.

**Успех:** оператор за минуту находит модель из ответа ИИ (наш товар или запись реестра), закрепляет её за лотом с
заметкой «почему», видит сверку ТЗ с этой моделью, и дальше модель идёт в работу сама: в письмо запроса цен, в подбор
поставщиков, в заявку на участие.

## 2. Решения оператора (2026-10-20)

1. Закреплять можно **наш товар с сайта или любую модель из реестра НЦЭЛС** — поиск по названию, производителю или № РУ
   в одном окне (без моделей вне реестра: больнице продать можно только зарегистрированное в РК).
2. Модель из реестра **сверяется с ТЗ так же, как наш товар** — по своей карточке РУ ndda.kz.
3. Подход 1: **«модель в работе» = нынешняя предложенная модель лота** — одно понятие, нижние пути (письмо, поставщики,
   заявка на участие) не меняются.
4. Доработка UI сравнения на больших ТЗ и сильные «◐ похоже» в списке — **в бэклог** (CLAUDE.md §16 «Сверка ТЗ — что дальше»).

## 3. Как работает (сценарий)

1. Оператор в карточке тендера жмёт «📋 Для ИИ», вставляет текст в Claude, получает совет: «ДКИ-Н-12 подходит по 30 из 34;
   или Mindray BeneHeart D3, РУ РК МИ (МТ)-0№…».
2. В раскрытом лоте — «📌 Модель…» → окно: набирает «ДКИ» или номер РУ → выбирает строку → вставляет вывод ИИ в
   «Почему эта модель» → «Закрепить». Наш товар-кандидат из «Сверки с нашим товаром» закрепляется и одной кнопкой
   «📌 Закрепить».
3. Шапка лота: «📌 Модель в работе: ДКИ-Н-12 (Аксион) · наш товар · РУ ✓», под ней — заметка. В блоке сверки первой идёт
   «Сверка с моделью в работе».
4. «КП» по лоту → письмо поставщику уже с этой моделью («— <модель> (<бренд>), РУ № … — N шт.»), подсказки поставщиков —
   по её бренду; ответы → «Собрать из КП» → заявка на участие с этой моделью. Всё это уже работает от предложенной модели.
5. В «Истории» тендера: «Лот «Дефибриллятор»: модель в работе — ДКИ-Н-12 (Аксион)» с автором; в списке тендеров — чип
   «📌 ДКИ-Н-12» и фильтр «📌 С моделью в работе».

## 4. Данные (V40)

- `med_equipment.site_product_id BIGINT NULL REFERENCES site_product(id) ON DELETE SET NULL` + частичный уникальный
  индекс `(site_product_id) WHERE site_product_id IS NOT NULL`: позиция каталога, заведённая из нашего товара сайта, —
  одна на товар; по связи АИС знает, что модель в работе — наш товар.
- `tender_lot.model_note VARCHAR(1000)` — «почему эта модель» (вывод ИИ), `model_set_by VARCHAR(100)`,
  `model_set_at TIMESTAMPTZ` — кто и когда закрепил. Пишутся при любой установке и снятии модели.
- Событие сделки — `deal_event` типа STAGE с кодом `MODEL` (схема не меняется).

## 5. Сервер

### 5.1 Одна точка для модели лота — `LotModelService`

Все пути, ставящие или снимающие предложенную модель, идут через `LotModelService.apply(lot, equipment, note)` /
`clear(lot)`: новое окно, «Взять в работу» в «Подборе» (`RegistryMatchService.adoptForLot`) и в комплектности
(`ComplectService.adoptComponent`), «Утвердить» в подборе по каталогу и `POST / DELETE /api/lots/{id}/proposed-equipment`.
Служба ставит `proposed_equipment`, `model_set_by` (`CurrentUser.name()`), `model_set_at`, заметку (новая модель без
заметки её очищает — заметка относилась к прежней модели) и пишет событие сделки в той же транзакции:
«Лот «<наименование лота>»: модель в работе — <модель> (<производитель>)», снятие — «Лот «…»: модель снята».

Гарды: лот только своего рынка (404; `findById` фильтр рынка не режет — CLAUDE.md §14), позиция каталога своего рынка
(404); наш товар и запись реестра — только на KZ (400 «Только для Казахстана»); товар сайта снят с сайта (`removed_at`) —
400; заметка длиннее 1000 — 400. Запись — ADMIN.

### 5.2 Закрепить наш товар — `pinSiteProduct(lotId, siteProductId, note)`

Позиция каталога по `site_product_id` или новая: наименование (до 255), производитель — бренд товара (пусто — «не указан»),
РУ — запись реестра по № РУ товара (сравнение нормализованных номеров `RegNumbers.normalize`; нашлась — `REGISTERED` и
связь, нет — `UNCHECKED` без связи), `spec` — краткое описание товара, рынок KZ. Существующая позиция не перезаписывается,
кроме наименования и производителя, если товар на сайте переименован.

### 5.3 Закрепить модель реестра — `pinRegistry(lotId, regNumber, note)`

Позиция каталога — как сейчас в `adoptForLot` (по РУ или новая). Затем, ВНЕ транзакции, загрузка карточки РУ с ndda.kz,
если её ещё нет (`RegistryDetailService.detail`), чтобы была сверка; сбой ndda.kz закреплению не мешает.

### 5.4 Поиск — `GET /api/lots/{id}/model-search?q=`

Любой вошедший, только KZ (иначе 400), `q` — от 2 символов, до 200. Ответ `{ours: [...], registry: [...]}` до 10 строк в
группе:
- **ours** — товары сайта рынка KZ без `removed_at`: каждое слово запроса — в названии, бренде или артикуле (без учёта
  регистра, «ё» = «е»); строка — `productId, name, brand, sku, regNumber, regStatus, regExpires, url`; статус РУ — из
  снимка каталога (`CatalogSnapshot.card(id)`).
- **registry** — `RegistryMatchService.search(q, 10)` (слова в наименовании или у производителя); если в `q` есть цифры —
  сначала точное совпадение по нормализованному номеру РУ (`RegNumbers.normalize`); строка — `regNumber, name, producer, country, expires,
  unlimited, expired`.

### 5.5 Закрепить, заметка, снять

- `POST /api/lots/{id}/model` `{siteProductId | regNumber, note}` (ADMIN; ровно одно из двух, иначе 400) → лот.
- `PUT /api/lots/{id}/model-note` `{note}` (ADMIN; модели нет — 400) → лот: заметку можно дописать после быстрого
  закрепления.
- `DELETE /api/lots/{id}/model` (ADMIN) → лот; прежний `DELETE /proposed-equipment` — то же самое.

В ответе лота (`TenderLotResponse`) — `modelNote`, `modelSetBy`, `modelSetAt`; у `proposedEquipment` — ещё
`siteProductId`, `productUrl` (товар сайта), `source` (SITE / REGISTRY / CATALOG), `regExpires`, `regActive`.

## 6. Сверка модели в работе — `GET /api/lots/{id}/model-fit`

Любой вошедший, лот своего рынка. Ответ: `{model, note, setBy, setAt, card: OK | MISSING | NONE, error, fit}`, где `fit` —
`FitCandidate` (те же поля и строки, что у кандидатов «Сверки с нашим товаром»), `null` — модели нет.

- **Текст ТЗ** — тот же, что у отметки «наш товар»: общий помощник `ProductMatchService.lotFitText(lot)` (вынести из
  `evaluate`: разобранное ТЗ — раздел характеристик, иначе описание лота с площадки).
- **Карточка:**
  - наш товар (`site_product_id`) — `CatalogSnapshot.card(id)` (сайт + РУ, как у кандидатов); товара нет в снимке —
    карточка из БД тем же `ProductCards.of`;
  - модель реестра — `ProductCards.ofRegistry(MedRegistry)`: факты — числа кратких характеристик карточки РУ (источник
    «РУ»), слова — наименование, назначение, область применения, характеристики; статус РУ — по сроку в реестре
    (бессрочно или срок не раньше сегодняшней даты KZ — действует, иначе истекло). Карточка РУ ещё не загружена —
    загрузить (сеть вне транзакции); сбой — `card: MISSING` и текст «карточка РУ недоступна» (экран — «повторить»);
  - позиция каталога без товара сайта и без РУ (подбор по каталогу) — факты из её `spec`, `card: OK`; без `spec` — `NONE`.
- **Правила** — `SpecFit.compare` (вердикт, отметки ✓ / ✗ / ≈ / «нет данных», «у нас: …»), ничего не хранится:
  сверка всегда по свежему тексту ТЗ и карточке.

## 7. Экран

- **Шапка лота** (`tender-lots`): «📌 Модель в работе: <модель> (<производитель>) · наш товар / реестр · РУ ✓ / РУ истекло
  ДД.ММ.ГГГГ / РУ не найдено», ссылка ↗ на товар сайта, «✕» — снять (админ); под строкой — заметка (приглушённо, до двух
  строк, полностью — по нажатию). Чип стадии «Модель выбрана» — как был.
- **«📌 Модель…»** в действиях раскрытого лота (админ, KZ) → окно `lot-model-dialog` (`@defer`): поле поиска (пауза 300 мс,
  от 2 символов), группы «Наши товары (westmed.kz)» и «Реестр НЦЭЛС», выбор строки → поле «Почему эта модель (можно
  вставить вывод ИИ)» → «Закрепить»; модель уже есть — «Заменить …?». На телефоне — во весь экран, цели 40 px; Esc и фон
  закрывают (во время запроса — нет).
- **Блок сверки** (`lot-fit`): при модели в работе первой идёт «Сверка с моделью в работе: <модель>» (тот же вид строк,
  «карточка РУ недоступна — повторить»), заметка и «изменить заметку»; ниже — «Сверка с нашим товаром», у каждого нашего
  кандидата — «📌 Закрепить» (админ); у лота без нашей отметки — «Требования ТЗ» и «📌 Модель…».
- **Список тендеров:** чип «📌 <короткое наименование>» (одна модель; несколько лотов — «📌 2 модели»), фильтр «Наш товар»
  → «📌 С моделью в работе» (`TenderResponse.modelsInWork` — одним запросом на страницу).
- **«📋 Для ИИ»** (`ProductAiBrief`): у лота — «Модель в работе: <модель> (<производитель>), РУ … — <статус>; закрепил
  <кто> <дата>; почему: <заметка>» и сверка АИС этой модели (✓ / ✗ / ≈ / нет данных) — чтобы ИИ мог её перепроверить.
- **«История» тендера:** события `MODEL` — строкой с автором.

## 8. Что не меняется

Письмо запроса цен (позиции из предложенной модели), подбор поставщиков по бренду модели, «Собрать из КП» и заявка на
участие, отметки «наш товар», уровни и Telegram «Нашей продукции», частные заявки (у них своя «Найти на westmed.kz»), рынок РФ
(подбор по каталогу — как был, теперь с «кто и когда» и событием).

## 9. Ограничения

- Ответ ИИ АИС не разбирает — модель выбирает оператор.
- Одна модель на лот.
- РУ нашего товара, которого нет в локальной копии реестра (9 номеров из 37 на 2026-10-20), к позиции каталога не
  привязывается — письмо поставщику уйдёт без «РУ №»; статус РУ товара на экране — из проверки ndda.kz (как в «Товарах»).
- Статус РУ модели реестра — по сроку в локальной копии реестра, не живой.
- Сверка модели реестра — только по карточке РУ: если в ней мало чисел, будет «нет данных».

## 10. Проверка

- Тесты: `ProductCards.ofRegistry`; `LotModelService` (наш товар — новая позиция и повторно та же, связь, РУ по
  нормализованному номеру; модель реестра; заметка и её очистка при смене модели; событие; гарды — чужой рынок 404, РФ
  400, снятый товар 400, длинная заметка 400); старые пути (`adoptForLot`, `adoptComponent`, `proposed-equipment`)
  пишут «кто и когда» и событие; поиск (слова, точный № РУ первым); `model-fit` (наш товар, реестр, каталог, карточки нет
  и ndda.kz недоступен); API — оператор 403 на запись, 200 на чтение; `modelsInWork` в списке; строка в «Для ИИ».
  Каждый тест — красный до правки, мутации ловятся.
- Полный прогон; `npm run build`.
- Живьём (локально, 1280 / 390, обе темы, оператор, РФ): закрепить наш товар из окна и кнопкой у кандидата, модель
  реестра по номеру РУ, сверка обеих, заметка, снять; предпросмотр письма КП по лоту — закреплённая модель; «История»;
  чип и фильтр в списке; «Для ИИ».

## 11. Вне рамок

Разбор ответа ИИ, несколько моделей на лот, модель вне реестра свободным текстом, «модель в работе» у частных заявок и на
РФ (кроме записи «кто и когда»), доработка UI сравнения на больших ТЗ (бэклог).
