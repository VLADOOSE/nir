# Мобильная эргономика: спроектированные карточки вместо механических простыней — дизайн

**Дата:** 2026-07-29
**Статус:** утверждён оператором (принцип выбран явно; остальные решения делегированы исполнителю)
**Контекст:** CLAUDE.md §12 (мобильный адаптив, UI-kit), §16 «СЛЕДУЮЩИЙ ШАГ». Предыдущий заход (тёмная тема) сознательно вывел мобилку из объёма и копил находки.

## Проблема

Мобильный адаптив в проекте есть с 2026-07-15: брейкпоинт 900px, drawer-сайдбар, и глобальный паттерн «таблица → карточки» (`table.responsive-cards` + `data-label` на каждой `<td>`). Формально он работает — горизонтального скролла на списках нет.

Но это **механическое** преобразование: каждая колонка становится строкой «подпись: значение». На широкой таблице получается простыня. Замер на реальных данных (390×844, `/applies`, 141 заявка):

| | было |
|---|---|
| колонок в таблице | 9 |
| высота карточки | **307 px** |
| карточек на экран | **2,7** |
| прокрутки на весь список | **51 экран** |

Для сравнения — список лотов, спроектированный под мобилку осознанно в заходе 2026-07-27: свёрнутая карточка 62px, 50 лотов = 4,3 экрана. Разница не в наличии адаптации, а в том, что одна сделана механически, а другая — по смыслу.

Второй класс проблем — таблицы, которые вообще не адаптированы или обёрнуты в горизонтальный скролл (`.table-scroll`): матрица сравнения предложений, ввод цен по КП, `smart-match`, карточка оборудования, карточка частной заявки, отчёты.

## Решение оператора

**Принцип: осмысленная карточка на каждый экран.** По каждому списку решаем, что оператор реально читает глазами при просмотре, и только это кладём в карточку; остальное живёт в карточке записи. Отвергнут вариант «просто скрыть второстепенные колонки» — он даёт «таблицу без лишнего», а не вещь, спроектированную под телефон.

Остальные решения (объём, порядок, конкретные раскладки) оператор делегировал: «где надо выбрать — выбирай сам исходя из лучших соображений».

## Механизм: строка-грид с адресацией по `data-label`

Прототип проверен вживую на `/applies` до написания спеки.

```scss
@media (max-width: 900px) {
  table.responsive-cards tr {
    display: grid;
    grid-template-columns: 1fr auto;
    grid-template-areas:
      "num   status"
      "cust  cust"
      "sum   cnt"
      "act   act";
  }
  td[data-label="Номер тендера"] { grid-area: num; font-weight: 600; }
  td[data-label="Статус"]        { grid-area: status; justify-content: flex-end; }
  td[data-label="Заказчик"]      { grid-area: cust; color: var(--text-muted); }
  td[data-label="ID"]            { display: none; }
  td:not([data-label])           { grid-area: act; }
}
```

**Результат прототипа:** 307px → **124px**, 2,7 → **6,8** карточек на экран, 51 → **21** экран прокрутки.

Почему именно так:

- **Нет дублирования разметки.** Альтернатива — держать отдельный блок карточек для мобилки и таблицу для десктопа — удваивает шаблон и разъезжается при первой же правке.
- **Адресация по `data-label`, а не по `nth-child`.** Порядок колонок меняется — раскладка не ломается. И правило читается как документация: видно, какая колонка куда идёт.
- **Десктоп не трогается вообще**: всё внутри `@media (max-width: 900px)`.
- **Опирается на то, что уже есть.** `data-label` проставлены на 10 экранах ещё в 2026-07-15 — их не надо заводить заново.

Скрывать на мобилке (`display: none`) — то, что не участвует в просмотре списка: технические идентификаторы, даты создания, служебные счётчики. Это не потеря данных: всё видно в карточке записи.

## Объём

### Волна A — списки (главная боль)

Порядок по величине простыни (число `data-label` в строке):

| Экран | колонок | что оставить в карточке |
|---|---|---|
| `applies` | 9 | номер тендера · статус · заказчик · сумма · позиций |
| `facilities` | 7 | название · город/регион · контакт |
| `distributors` | 6 | название · бренды · email |
| `equipment` | 5 | название · производитель · тип |
| `inbound` | 5 | тема · отправитель · тип · получено |
| `private-requests` | 5 | номер · клиент · позиций · статус |

`users` (3), `equipment-types` (1), `dashboard` (4), `registry-reconciliation` (4) — 3–4 строки в карточке приемлемы; трогать только если живая проверка покажет, что мешает.

### Волна B — горизонтальный скролл

- **`offer-comparison`** — матрица лоты × поставщики. Самый сложный случай: на телефоне матрица не работает в принципе. Решение — переворот: карточка на ЛОТ, внутри список предложений поставщиков, минимум подсвечен. Это редизайн, а не адаптация.
- **Ввод цен по КП** (`tenders.component.ts`) — таблица позиций с полями ввода.
- **`smart-match`** — таблица кандидатов.
- **`equipment-detail-modal`** — три таблицы характеристик.

### Волна C — без адаптации вовсе

- **`private-request-card`** — таблицы позиций в дровере.
- **`reports`** — таблицы + `.summary-grid` на `repeat(3, 1fr)`, который на 390px не сжимается ниже min-content (гоча §14).
- **`.lot-mini`** — чипы лотов на карточках списка тендеров скроллятся вбок (замер: 666→320px).
- **Тач-таргеты** — добить то, что осталось меньше 36px.

## Границы

- **Десктоп не меняется.** Всё новое — внутри `@media (max-width: 900px)`. Правило проверяется на каждой волне.
- **Только фронт.** Бэкенд не трогается.
- **Цвета — только существующие токены.** Новых красок не вводить; работа с цветом закончена прошлым заходом.
- **Разметку править МОЖНО** (в отличие от прошлого захода): расстановка `data-label`, вынос действий в overflow-меню, перестройка блоков — это и есть предмет работы. Но менять логику и данные нельзя: `*ngIf`-условия, интерполяции, обработчики остаются.

## Критерии готовности

- Ни один список не требует больше ~2 экранов прокрутки на первые 10 записей.
- Горизонтального скролла нет нигде, кроме мест, где он осознанно оставлен и прокомментирован.
- На 390px нет элементов шире вьюпорта и нет тач-таргетов меньше 36px в основных потоках.
- Десктоп на 1280px не изменился — проверяется замером до/после, как делали с тёмной темой.
- Обе темы в порядке (работа идёт поверх завершённой токенизации).
