# Тёмная тема на остальных экранах через глобальный UI-kit — дизайн

**Дата:** 2026-07-27
**Статус:** утверждён оператором
**Контекст:** CLAUDE.md §12 (тёмная тема, фронт), §16 «СЛЕДУЮЩИЙ ШАГ»; PROGRESS §4 п.0

## Проблема

Тёмная тема введена 2026-07-19 и в проде с 2026-07-27, но токенизированы только **каркас** (`layout`) и **страница тендеров** (`tenders`, `tenders-filters`, `tender-lots`, `lot-kp-panel`, `lot-registry-panel`). Остальные 24 компонента держат цвета захардкоженными хексами → в тёмном режиме дают светлые пятна. Два из них (`confirm`, `notification`) — глобальные оверлеи, светятся **на любой** странице, включая уже готовую страницу тендеров.

Замер 2026-07-27 (`grep -oE '#[0-9a-fA-F]{3,8}'` по `*.component.ts`):

- **~845 вхождений хексов в 24 компонентах**, но всего **69 различных значений**;
- топ-10 значений покрывают ~70% вхождений — это тейлвиндовская серая палитра + бренд-синий `#1a56db`;
- CSS **сильно дублируется между компонентами** (считано по числу файлов, где класс *объявлен*, а не по вхождениям): `.empty` — 14 файлов, `.subtitle` — 13, `.btn-cancel` — 12, база `th, td` — 11, `.badge*` — 11, `.btn-save` — 9, `.form-actions` — 9, `.btn-add` — 8, `.error-banner` — 8, `.counter` — 8, `.field-error` — 8, `.btn-edit`/`.btn-delete` — 7, `.btn-line` — 6, `.btn-primary` — 5. Один и тот же `.btn-cancel { background:#e5e7eb; color:#374151 }` переписан 12 раз.

Прямой перевод «в лоб» (hex→токен в каждом файле) сделал бы ~845 замен и оставил дублирование: следующий новый экран снова скопирует хексы и снова будет светиться.

## Решения оператора (зафиксированы в брейншторме)

1. **Сначала UI-kit**, потом по-экранная зачистка — не прямой перевод.
2. **Только тема.** Мобильную эргономику в этом заходе **не чиним**: каждый экран всё равно смотрим живьём на 390px, но найденные проблемы идут со скринами в отчёт → вход для следующего захода.
3. **Токены + унификация из kit.** В светлой теме вид может измениться там, где экраны сейчас расходятся между собой (разные padding/радиусы кнопок, разные формы бейджей). Редизайна макетов/типографики нет.
4. **Пуш в `main` после каждой волны** (= автодеплой в прод), а не одним куском в конце.

## Архитектура решения

### Почему kit безопасен: специфичность

Angular-scoped стиль компилируется в `.btn[_ngcontent-abc]` — специфичность (0,2,0). Глобальный `.btn` из `styles.scss` — (0,1,0). **Скоуп всегда перебивает глобальный.**

Отсюда главное свойство плана: **Волна 0 вливается с нулевым визуальным эффектом.** Kit «спит» под каждым компонентом, пока в компоненте лежит собственный блок. Переход становится по-экранным, обратимым и проверяемым: удалили локальный блок — проснулось глобальное правило.

Для базовых элементов (`table`, `th`, `td`, `input`, `h2`) используем **элементные селекторы** (специфичность 0,0,1) — их перебивает вообще любое компонентное правило, включая элементное скоупнутое `th[_ngcontent-x]` (0,1,1).

### Слои kit в `frontend/src/styles.scss`

**(а) Компонентные классы** — только те, чьи имена реально повторяются в 5+ файлах:

- `.btn` + семантические варианты:
  - accent: `.btn-primary`, `.btn-add`, `.btn-save`, `.btn-open`, `.btn-login`, `.btn-search`
  - нейтраль: `.btn-cancel`, `.btn-back`, `.btn-close`, `.btn-reset`, `.btn-reset-filter`
  - danger: `.btn-delete`, `.btn-danger`, `.btn-pdf`
  - warn: `.btn-edit`
  - outline: `.btn-line` (`background: var(--surface); border: 1px solid var(--border)`)
- `.badge` + тинты известных статусов: `DRAFT/ACTIVE/SUBMITTED/COMPLETED/WON/LOST/CANCELLED/REJECTED/UNDER_REVIEW`, семейства `.badge-pr-*`, `.badge-d-*`
- `.empty`, `.subtitle`, `.error-banner`, `.counter`, `.field-error`, `.form-actions`

**(б) Базовые элементы — только цветовые свойства, без геометрии:** `table/th/td`, `input/select/textarea`, `h2/h3`.

Геометрию (padding, radius, font-size) в этот слой **не кладём**: она у экранов разная, и менять её глобально — это уже редизайн, которого в заходе нет. Смысл слоя — страховочная сетка: экран, до которого волна ещё не дошла, перестаёт светить белым там, где цвет не задан явно.

**(в) Модалки в kit НЕ идут.** Бэкдропы называются по-разному в каждом компоненте (`.confirm-overlay`, `.af-modal-backdrop`, `.modal-backdrop`, `.kp-preview-backdrop`), унификация требует правки шаблонов — не окупается. Переводим по месту.

### Таблица соответствия hex → токен

**Не изобретена — извлечена из фактических коммитов `81b3baa`/`b8a8e14`** (токенизация каркаса и страницы тендеров, в проде). Новые экраны обязаны переводиться ровно так же, иначе приложение расслоится на два диалекта.

| Хекс | Токен | Комментарий |
|---|---|---|
| `#111827`, `#374151` | `var(--text)` | два оттенка текста схлопываются в один |
| `#6b7280`, `#9ca3af` | `var(--text-muted)` | схлопываются |
| `#e5e7eb`, `#d1d5db` | `var(--border)` | схлопываются |
| `#f3f4f6`, `#f9fafb` | `var(--surface-2)` | схлопываются |
| `#fff`, `#ffffff` | `var(--surface)` — фон; `var(--accent-contrast)` — текст на цветной кнопке | **по контексту** |
| `#1a56db`, `#1e40af`, `#1e3a8a`, `#2563eb` | `var(--accent)` | |
| `#ef4444`, `#dc2626`, `#b91c1c`, `#991b1b` | `var(--danger)` | |
| `#f59e0b`, `#92400e`, `#b45309` | `var(--warn)` | |
| `#059669`, `#065f46`, `#10b981`, `#047857`, `#166534` | `var(--success)` | |
| `box-shadow: 0 2px 8px rgba(0,0,0,.08)` | `var(--shadow)` | |

**Светлые тинты** (`#dbeafe`, `#eff6ff`, `#fef3c7`, `#d1fae5`, `#fee2e2`, `#fef2f2`, `#ecfdf5`, `#dcfce7`, `#eef2ff`, `#a7f3d0`, `#bbf7d0`, `#e0e7ff`) — по роли:

- **чип/бейдж** (мелкий элемент): `background: color-mix(in srgb, var(--TOKEN) 15%, transparent); color: var(--TOKEN)`
- **подсветка области** (строка таблицы, карточка, панель): `background: color-mix(in srgb, var(--TOKEN) 8%, var(--surface))` **+ рамка** `border-color: var(--TOKEN)`

⚠️ **Урок, оплаченный багом.** При токенизации тендеров подсветку строки `tr.kp-hit td { background:#ecfdf5 }` перевели наивно в `var(--surface-2)`. Результат: `--surface-2` совпал с фоном самой панели → преотмеченные (сильнейшие) поставщики утонули в фоне, а слабые светились белым — **инверсия смысла**, чинили отдельным коммитом `6b8dc3f`. Отсюда правило выше: подсветка области смешивается с `--surface` (непрозрачно) и подкрепляется рамкой, а **не** заменяется на `--surface-2`.

**Фикс-цветные кнопки остаются хексами** — по решению оператора (CLAUDE.md §12): `#0e9f6e` («КП», зелёная), `#6366f1` («ТЗ», индиго), `#8b5cf6` (bulk). Читаются в обеих темах. Меняется только `color: #fff` → `var(--accent-contrast)`.

### Что делает исполнитель на каждом компоненте

1. **Удалить** блоки, покрытые kit (`.btn-*`, `.badge-*`, `th, td`, `.empty`, `.subtitle`, `.error-banner`, `.counter`, `.field-error`, `.form-actions`).
2. **Перевести** оставшиеся хексы по таблице соответствия.
3. **Оставить локально** только то, где домен расходится с kit. Пример: в `applies` статус `CANCELLED` — нейтральный («заявка отменена»), а в тендерах красный; остаётся одна строка-переопределение на токенах, а не восемь.
4. `@media` — **последним блоком** в `styles` (CLAUDE.md §14: при равной специфичности позднее базовое правило молча перебивает раннюю @media-переопределялку).

## Проверка

**Гейт волны:**

1. `cd frontend && npm run build` — зелёный (бюджет `anyComponentStyle` 24 kB; удаление дублей его только освобождает).
2. Живой Playwright-обход **каждого** тронутого экрана в 4 состояниях: 1280 / 390 px × светлая / тёмная.
3. **Регресс-проход по странице тендеров** после Волны 0 и после Волны 1 (kit трогает глобальное пространство — уже готовые экраны обязаны остаться прежними).

**Риск Волны 0 — что именно kit «разбудит» досрочно.** Проверено скриптом при планировании (строгий матч класса как отдельного токена в `class="…"`, а не как части дефисного имени — наивный `\bbtn\b` даёт ложные срабатывания на `btn-logout`, `score-badge`, `lrp-empty`):

- **Уже токенизированные компоненты не затрагиваются вовсе.** Ни один из `tenders`, `tender-lots`, `lot-kp-panel`, `lot-registry-panel`, `tenders-filters`, `layout` не полагается на необъявленный kit-класс. Утверждение «Волна 0 вливается с нулевым визуальным эффектом» для готовых экранов подтверждено.
- **Пять непереведённых экранов изменятся до своей волны**, потому что используют kit-класс, которого сами не объявляют: `equipment-types` (`.btn-save`), `login` (`.btn`), `reports` (`.btn`), `private-requests` (`.empty`), `registry-reconciliation` (`.empty`). Сейчас эти элементы стоят без стиля (браузерный дефолт), так что изменение ожидается в лучшую сторону — но проверить надо.
- **Три компонента содержат `<table>` без собственных табличных стилей** — `smart-match`, `offer-comparison`, `inbound`. Их шапки получат цвет из kit. Первые два лежат в Волне 1 и всё равно переделываются; `inbound` живёт в Волне 2, поэтому его смотрим отдельно сразу после Волны 0.

**Сбор мобильных проблем:** на проходе 390px фиксировать скринами экраны, где оператору неудобно (горизонтальный скролл плотной таблицы, обрезка, налезание). Не чинить. Итог — раздел отчёта → §16 как вход следующего захода.

## Границы (чего в заходе нет)

- Редизайна макетов, типографики, отступов, иерархии.
- Переделки таблиц в карточки-аккордеоны (решение оператора: отдельный заход).
- Бэкенда — ни строки.
- Трёх хвостов из §16 (403 при снятии вида МИ у лота; `takeUntilDestroyed` в вынесенных панелях; доступность шапки лота-аккордеона) — они не про тему.

## Критерии готовности

- В тёмной теме ни один из 24 экранов не даёт белых пятен на фоне тёмного каркаса.
- В светлой теме расхождения возможны только там, где экраны раньше противоречили друг другу; ни один экран не стал хуже.
- `.btn-*`, `.badge-*`, `.empty`, `.subtitle`, `.error-banner`, база таблиц объявлены **один раз** в `styles.scss`.
- Новый экран, написанный после этого захода на классах kit, получает тёмную тему без дополнительной работы.
- Отчёт по мобильным проблемам со скринами приложен, приоритетный список внесён в §16.
